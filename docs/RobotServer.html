01 Purpose & Role in the System

RobotServer is the one and only process that runs on the robot's own onboard computer (a Raspberry Pi or similar single-board computer, physically mounted on the robot). Its job is to bridge the ROS2 robotics software — navigation, mapping, motor control, sensors — to the outside world over ordinary web protocols (HTTP, WebSocket, WebRTC).

ROS2 ("Robot Operating System 2") is the robotics middleware the rest of the robot's software is built on: localization, path planning (Nav2), SLAM mapping, motor drivers, the LED/sensor microcontroller bridge. ROS2 nodes talk to each other using topics (fire-and-forget broadcast channels), services (one-shot request/response calls), and actions (long-running, cancelable, progress-reporting tasks like "drive to this point"). None of that is reachable over the internet or from a browser by default — RobotServer's entire reason for existing is to translate between "ROS2 node talking to other ROS2 nodes" and "web client talking over HTTP/WebSocket."

It replaces an older Python service (WebServer/, FastAPI + rclpy) that had accumulated duplicated routes, no mutual exclusion between launch processes, hardcoded database credentials, and other issues documented in the project's README. RobotServer is a ground-up rewrite in Node.js/TypeScript, deliberately mirroring the architecture of PlatformServer (the cloud backend) for consistency across the whole codebase.

Three kinds of things talk to RobotServer

  • RobotApp — a React single-page app that is the robot's own touchscreen UI. It is served by its own small container (nginx), which reverse-proxies /api, /ws, /maps, and /health back to RobotServer on localhost:8000. This keeps the browser on one origin, so RobotServer's login cookies "just work" with no cross-origin complications.
  • PlatformServer (the cloud/VPN-hosted backend) — RobotServer makes outbound calls to PlatformServer: one-shot REST calls via platformClient.ts, and one persistent outbound WebSocket connection via platformLink.client.ts. RobotServer never listens for inbound connections from PlatformServer directly — PlatformServer instead calls one RobotServer HTTP endpoint (/api/platform-auth/roster/invalidate) over the VPN/public internet.
  • ROS2 itself — via the rclnodejs library (a JavaScript/Node.js binding for ROS2's client library, playing the same role Python's rclpy plays elsewhere). RobotServer runs as a single ROS2 "node" and uses it to publish/subscribe to topics, call services, and send actions to Nav2, SLAM, and the ESP32 firmware bridge.

Remote users (browser dashboard, Android app) no longer connect to RobotServer directly at all in this version — all remote teleop/control is relayed through PlatformServer's /ws/robot-link, with RobotServer as the outbound-only client. This means RobotServer's only exposed network surface is localhost-proxied RobotApp traffic plus its one outbound connection to PlatformServer — a deliberate security posture with no inbound attack surface from the internet.

02 Tech Stack Explained

Every dependency below is explained in plain English, with where and why it's used in this codebase.

TypeScript

JavaScript with optional static types checked before the code runs.

Where: the whole codebase under src/; tsconfig.json runs in strict mode with noUnusedLocals/noUnusedParameters to catch dead code.

Node.js

The JavaScript runtime that lets JS/TypeScript run as a standalone server process outside a browser.

Where: the entire backend; src/index.ts is the process entrypoint.

Express

A minimalist web framework: define "routes" (e.g. POST /api/navigation/start) and attach handler functions, plus "middleware" that runs on every request.

Where: the whole HTTP layer — src/app.ts (composition root) and every *.routes.ts file.

rclnodejs

The JS/TypeScript client library for ROS2 — the Node.js equivalent of Python's rclpy. Lets a Node process become a real ROS2 node.

Where: exclusively inside src/ros/* — a hard rule states "nothing outside this folder imports rclnodejs directly." Pinned to 2.x, which supports ROS2 "Lyrical" (the distro this repo targets) as well as Kilted/Jazzy/Humble/Rolling.

ws

A WebSocket server/client implementation — a persistent, two-way connection unlike one-shot HTTP request/response.

Where: src/core/wsRouter.ts (incoming connections on the robot) and src/clients/platformLink.client.ts (outbound link to PlatformServer).

werift

A WebRTC implementation for Node.js — peer-to-peer real-time audio/video/data, so a viewer can watch the camera feed without routing video through a server.

Where: video.wsServer.ts (signaling handshake) and ffmpegVideoSource.ts (feeding frames — currently an unimplemented stub).

Mongoose

An Object-Document Mapper for MongoDB: define a "Schema" as a TypeScript class and get back a typed "Model" for reads/writes.

Where: saved goal poses (goal.model.ts) and cached local-login users (localUser.model.ts). Connection in src/db/connection.ts.

MongoDB GridFS

A MongoDB convention for storing large binary files bigger than the normal per-document size limit, inside the database itself.

Where: maps/map.repository.ts, storing saved map PNG + YAML files so they survive a container being recreated.

Zod

A TypeScript-first schema validation library — describe the shape data should have, and it validates at runtime and derives a matching TypeScript type.

Where: every environment variable (config/env.ts), every HTTP request body (*.validation.ts), and PlatformServer link messages (teleopLink.protocol.ts).

jsonwebtoken (JWT)

Cryptographically signed, tamper-evident tokens encoding a small payload without a database lookup to verify.

Where: RobotApp's human login session (access + refresh tokens), signed/verified in jwt.util.ts. Unrelated to the plain shared-secret ROBOT_LINK_SECRET scheme.

bcryptjs

A slow-by-design password/PIN hashing library, making a leaked hash expensive to brute-force.

Where: only to compare a PIN against an already-hashed value (pin.util.ts) — RobotServer never generates a hash; PlatformServer is the source of truth.

cookie-parser

Express middleware that reads the Cookie: header and populates req.cookies.

Where: src/app.ts, paired with cookie.util.ts which sets security flags (httpOnly, secure in production, sameSite: strict).

cors

Browser security mechanism middleware that blocks a page on one origin from calling an API on another unless explicitly allowed.

Where: configured from CORS_ORIGINS in src/app.ts; only applied if at least one origin is set.

helmet

Express middleware setting a batch of security-related HTTP response headers with sensible defaults.

Where: applied globally in src/app.ts.

pino / pino-http / pino-pretty

A fast structured logger, an Express middleware that auto-logs every request/response, and a dev-only human-readable formatter.

Where: logger.util.ts (JSON in production, pretty in dev, silent during tests), wired into Express in app.ts.

swagger-jsdoc / swagger-ui-express

Reads @openapi JSDoc comments above route definitions and turns them into a browsable, "try it out" API doc page.

Where: src/config/swagger.ts, mounted at GET /api/docs.

dotenv

Loads key=value pairs from a .env file into process.env at startup.

Where: top of src/config/env.ts.

Jest / ts-jest

A JS/TypeScript testing framework; ts-jest runs TypeScript test files directly with no separate compile step.

Where: tests/, run via npm test.

mongodb-memory-server

Dev dependency: spins up a real, temporary, in-memory MongoDB for tests that need one.

Where: not currently needed by tests/unit/ (the fakes pattern avoids Mongo entirely) — reserved for future integration tests.

supertest

Dev dependency for testing Express endpoints by firing real-ish requests at an app object in-process, with no network port bound.

Where: available for HTTP-level tests.

nodemon + ts-node

Dev-only tools: ts-node runs TypeScript directly without a compile step; nodemon watches and restarts on file changes.

Where: wired via nodemon.json and npm run dev.

ESLint + @typescript-eslint

Static code-quality/style checker for TypeScript.

Where: run via npm run lint.

04 Architecture Layers & Patterns

RobotServer uses a layered architecture: routes → controller → service → repository (interface) → repository (implementation) → model, explicitly modeled on PlatformServer's architecture for consistency across the codebase. Everything is wired together by hand in one "composition root" function, createApp() in src/app.ts — there is no dependency-injection framework; every class takes its dependencies as plain constructor arguments.

Why this layering exists: each layer only knows about the layer directly below it through an interface, not a concrete class. A layer can therefore be tested in complete isolation by handing it a hand-written "fake" that satisfies the same interface, instead of the real thing (a real ROS2 node, a real MongoDB). That's exactly what tests/unit/fakes/ contains: FakeRosTopicGateway, FakeRosServiceGateway, FakeRosActionGateway, FakeGoalRepository, FakeMapRepository, FakeLocalUserRepository, FakePlatformClient, FakeClock. Because of this, none of the unit tests under tests/unit/ require a running ROS2 node or a real MongoDB instance — they run in plain Node.js, fast, in any environment, including CI.

A second, narrower but important pattern: ROS2 access itself is organized by communication primitive, not by feature. Instead of, say, a NavigationGateway and a MappingGateway each owning their own ROS2 publisher/subscriber code, there are exactly three generic classes — RosTopicGateway, RosServiceGateway, RosActionGateway — and every feature service depends on whichever of the three it needs, calling it with the specific ROS2 topic/service/action name as a plain string argument (e.g. topicGateway.publish("geometry_msgs/msg/Twist", "cmd_vel", ...)). This is why TeleopService, NavigationService, MappingService, and FirmwareService all take one or more of these three gateways as constructor parameters, rather than each having a bespoke ROS2 wrapper class.

Concrete trace: "start navigation" (a navigation goal submission flow)

  1. Route — POST /api/navigation/goal/start is defined in navigation.routes.ts. It runs validate({ body: goalLookupSchema }) (Zod-checks the body has mapName and name strings) and then asyncHandler(navigationController.startGoal).
  2. Controller — NavigationController.startGoal pulls mapName/name from req.body, calls navigationService.startGoal(mapName, name), and on success responds 200 { status: "navigating" }. The controller contains no business logic — just request/response shaping.
  3. Service — NavigationService.startGoal calls its own private getGoal(mapName, name) (via the goal repository) to look up the saved pose, then calls sendGoal(pose), which: cancels any already-active goal (actionGateway.cancelGoal) and converts the saved 2D pose's theta (yaw) into a quaternion via quaternionFromYaw.
  4. Repository — the goal lookup goes through IGoalRepository.findOne(mapName, name) → MongooseGoalRepository.findOne → Mongoose's GoalModel.findOne(...) → MongoDB.
  5. Gateway — RosActionGateway.sendGoal("nav2_msgs/action/NavigateToPose", "navigate_to_pose", goalMsg, onFeedback, timeout) is the only place that actually calls rclnodejs's ActionClient.sendGoal(...), against the real (or faked, in tests) ROS2 action server.
  6. As the Nav2 action server reports feedback (distance_remaining) and eventually a result, the service's onFeedback callback updates this.feedback, and the result promise updates this.status (a NavStatus value). These are exposed via separate GET /api/navigation/goal/feedback and GET /api/navigation/status endpoints — polled by RobotApp — rather than pushed.

In tests (tests/unit/navigation.service.test.ts), the exact same NavigationService class is constructed with FakeRosActionGateway, FakeRosServiceGateway, FakeRosTopicGateway, a real TeleopService wired to a FakeRosTopicGateway, and FakeGoalRepository/FakeMapRepository — so the entire flow above runs in-process with no real ROS2 or Mongo, and the test can directly assert what goal message would have been sent.

05 Key Flows

Six flows cover everything that happens from process start to a human driving the robot. Each diagram below is a sequence view: columns are participants, vertical dashed lines are their lifelines, and numbered arrows are steps in time order, matching the step list underneath.

Flow A — Server boot sequence

Trigger: process start (node dist/index.js in production, nodemon + ts-node in dev).

  1. connectDatabase() opens the Mongoose/MongoDB connection.
  2. initRosNode() calls rclnodejs.init(), creates the ROS2 node (named robot_server), and starts it "spinning" (processing ROS2 callbacks).
  3. A DeviceIdentityService is constructed and resolveWithRetries(3) is called — it asks the ESP32 bridge (over a ROS2 Trigger service) "what is this robot's device id?" If it never answers after 3 attempts, boot continues anyway in a degraded state (a warning is logged) — local ROS2 functionality and PIN login must come up even with no ESP32/VPN connectivity yet.
  4. createApp(rosNode, deviceIdentity) runs the entire composition root (every gateway/repository/service/controller built and wired, Express routes mounted).
  5. A plain Node.js http.Server wraps the Express app; registerWebSockets(wsRouter) registers /ws/topics and /ws/webrtc on it; wsRouter.attach(server, authenticateFn) wires the WebSocket-upgrade routing in, authenticating by verifying the robotAccessToken cookie.
  6. A PlatformLinkClient is constructed and .start()ed — this begins the (async, retrying) process of dialing PlatformServer's /ws/robot-link (Flow E). It's wired into registerPlatformLink, which hooks teleopLink.handler.ts up to it.
  7. rosterSyncService.sync() runs once immediately (best-effort — failure only logged, not fatal) and then every ROSTER_SYNC_INTERVAL_MINUTES (default 60) via setInterval(...).unref() — the .unref() means this timer alone won't keep the process alive if everything else has shut down.
  8. server.listen(config.port, ...) — the HTTP server starts accepting connections.
  9. SIGTERM/SIGINT handlers are registered: on shutdown, stop the platform link, close the HTTP server, shut down the ROS2 node, then process.exit(0).

Flow B — HTTP request lifecycle (generic, applies to every REST call)

Trigger: any incoming HTTP request to RobotServer, directly or via RobotApp's nginx proxy.

  1. helmet() sets security headers.
  2. express.json() parses a JSON request body into req.body.
  3. cookieParser() parses Cookie: into req.cookies.
  4. cors(...) (only if CORS_ORIGINS is configured) checks the request's Origin.
  5. pinoHttp(...) logs the request (skipping /health to avoid log spam), and logs the response status on completion.
  6. The request reaches the mounted router for its path prefix (e.g. /api/navigation). If that prefix was mounted with requireAuth, the request must carry a valid robotAccessToken cookie or it's rejected with 401 here, before the route handler ever runs.
  7. Inside the matched route, validate({ body: ... }) (if present) runs the Zod schema; a failure throws a ZodError.
  8. The controller method runs (wrapped in asyncHandler, so a thrown/rejected error is forwarded via next(err) instead of crashing the process or hanging the request).
  9. If nothing threw, the controller writes the JSON response directly.
  10. If anything threw anywhere above, Express's error-handling chain reaches errorHandler, which maps ZodError → 400, any AppError subclass → its own status code, anything else → 500 (logged as unexpected).
  11. If no route matched at all, notFoundHandler returns a 404 JSON body instead of Express's default HTML error page.

Flow C — Telemetry: ROS2 topic → WebSocket broadcast to RobotApp

Trigger: ROS2 publishes new data on /map (occasionally) or on a 20Hz timer (location + nav status).

  1. At app startup, registerTelemetryBroadcast(topicGateway, navigationService) subscribes to the ROS2 topics /map (nav_msgs/msg/OccupancyGrid) and /amcl_pose (geometry_msgs/msg/PoseWithCovarianceStamped) via the shared RosTopicGateway.
  2. Every time a /map message arrives, its callback immediately converts it via mapOccupancyGridToMapUpdate and calls eventBus.emit("map", ...).
  3. A separate 20Hz timer (topicGateway.createTimer) reads the latest cached /amcl_pose message (via getLatest, not a per-message callback — avoids flooding on every pose tick), converts it via mapPoseToLocationUpdate, and emits eventBus.emit("location", ...); it also emits eventBus.emit("navStatus", { status: navigationService.getStatus() }) every tick.
  4. Separately, connectivity.broadcaster.ts polls PlatformServer's own /health every 15 seconds and emits eventBus.emit("robotStatus", { internetConnectivity }) only when that value actually changes.
  5. registerTopicsWebSocket (called once at boot) subscribed to all four eventBus event types when it registered /ws/topics; each event is immediately serialized and sent to every currently-connected socket as JSON.stringify({ type, data }).
  6. RobotApp's browser-side code connects to wss://<host>/ws/topics (proxied by nginx to RobotServer's localhost:8000) and receives these frames live.

WebSocket message schema (all frames on /ws/topics, server→client only, no client messages expected):

{ "type": "map", "data": { "info": {...}, "data": [...] } }
{ "type": "location", "data": { "x": 1.2, "y": -0.4, "theta": 0.78 } }
{ "type": "nav_status", "data": { "status": "ACTIVE" } }
{ "type": "robotStatus", "data": { "internetConnectivity": true } }

Flow D — Teleop command flow (remote browser/app → cmd_vel)

Trigger: a remote operator (browser dashboard, Android app) sends a joystick/drive command.

  1. A remote client does not connect to RobotServer directly at all in this version — it connects to PlatformServer, which relays the session over the persistent platformLink connection (PlatformLinkClient, the robot's outbound half of PlatformServer's /ws/robot-link).
  2. When a frame arrives on that socket, PlatformLinkClient's "message" handler JSON-parses it and calls every registered frame handler — the one registered is registerTeleopLinkHandler.
  3. The handler validates the raw frame against inboundLinkFrameSchema (a Zod discriminated union over type) — an invalid frame is logged and silently dropped, never crashes anything.
  4. For type: "teleop.velocity", it calls teleopService.setVelocity({ linear, angular }).
  5. TeleopService.setVelocity first checks getNavigationStatus() === NavStatus.ACTIVE — if Nav2 is actively driving the robot via its own NavigateToPose goal, the command is silently refused (logged at debug level) so remote teleop can never fight autonomous navigation. Otherwise it clamps the values to [-maxLinear, maxLinear]/[-maxAngular, maxAngular] (from TELEOP_MAX_LINEAR/TELEOP_MAX_ANGULAR config) and sets an expiry timestamp (clock.now() + ttlMs, default 500ms).
  6. A 20Hz timer (started in the constructor) calls publishTick() continuously: if the active command has expired with no refresh, it force-zeros; on any active→inactive or inactive→active transition it publishes one explicit edge-triggered frame; while steady-state active, it republishes the current commanded geometry_msgs/msg/Twist on the cmd_vel ROS2 topic every tick.
  7. Downstream, autonav_controller/cmd_vel_republisher.py (a separate ROS2 node, outside RobotServer) has its own 0.5s timeout matching this TTL, so a dropped connection or stalled command fails safe within half a second either way.
  8. For type: "teleop.estop": calls teleopService.setEmergency(engaged), which publishes directly onto /motor/emergency (std_msgs/msg/Bool) — bypasses the velocity/TTL machinery entirely.
  9. For type: "teleop.release": calls teleopService.stop() — an unconditional, immediate zero, even overriding an active Nav2 refusal.
  10. For type: "health.query": replies (via link.send(...)) with a health.result frame reporting rclOk (ROS2 node alive AND device id resolved), navigationActive, and this robot's real maxLinear/maxAngular limits, so a remote client can scale its joystick input correctly instead of guessing.

Inbound frame schemas (teleopLink.protocol.ts):

{ type: "teleop.velocity", sessionId: string, data: { linear: number, angular: number } }
{ type: "teleop.estop", sessionId: string, engaged: boolean }
{ type: "teleop.release", sessionId: string }
{ type: "health.query", id: string }

Outbound reply:

{ type: "health.result", id: string, rclOk: boolean, navigationActive: boolean, maxLinear: number, maxAngular: number }

No inbound teleop endpoint

There is no teleop.routes.ts / teleop.controller.ts and no inbound /ws/teleop WebSocket. The old server had a directly-reachable teleop WebSocket; this version deliberately removed it — the only way a remote client can drive the robot is through the outbound PlatformServer link described above. RobotApp (the local touchscreen) is expected to drive the robot some other way not present in this codebase as reviewed — likely a future local-only path, or it also goes through the same TeleopService via a mechanism not yet wired to a route.

Flow E — RobotServer ↔ PlatformServer persistent link (robot-link) registration & reconnection

Trigger: server boot, and continuously thereafter.

  1. platformLink.start() begins connectWhenIdentityReady(), which polls deviceIdentity.resolve() every 5 seconds until a robot ID is available (no identity → nothing to authenticate the link with, so it won't even attempt to dial).
  2. Once an ID is available, dial(robotId) opens a ws:// (or wss://, derived by swapping http→ws in PLATFORM_BASE_URL) connection to ${PLATFORM_BASE_URL}/ws/robot-link, sending x-robot-id: <robotId> and Authorization: Robot <ROBOT_LINK_SECRET> as headers.
  3. On "open", the reconnect backoff resets to 1 second, and a ping watchdog starts: every 12.5 seconds it checks whether a WebSocket protocol-level ping has arrived from PlatformServer within the last 25 seconds; if not, it force-terminates the socket (triggering the fail-safe + reconnect path below) — this detects a silently-dead TCP connection that never fires a clean close/error event.
  4. Incoming frames are JSON-parsed and handed to every registered handler (in practice, just teleopLink.handler.ts, wired via registerPlatformLink in app.ts).
  5. On any disconnect (clean close, error-triggered close, or the watchdog's forced termination) — teardownAndScheduleReconnect() runs this.teleop.stop() unconditionally, first, before anything else — described in the code as non-negotiable: no link means no remote supervision of motion, so motion must not continue unattended. Only after that does it compute a jittered exponential backoff (1s → doubling, capped at 30s, ±20% jitter) and schedule a reconnect attempt.
  6. send(frame) silently drops (with a debug log) anything sent while the link is down, rather than queuing or throwing.

Trust model: ROBOT_LINK_SECRET

ROBOT_LINK_SECRET is the only secret in the robot↔PlatformServer relationship (everything else relies on the VPN as the trust boundary). It's issued once at robot-provisioning time by PlatformServer; PlatformServer stores only its SHA-256 hash; losing it requires a rotation endpoint on PlatformServer (POST /api/admin/robots/:robotId/rotate-link-secret, per the .env.example comments — lives in PlatformServer, not reviewed here).

Flow F — Local PIN login (RobotApp touchscreen HMI session)

Trigger: a human stands in front of the robot and taps their name / enters an email on the touchscreen.

  1. GET /api/hmi-auth/users returns the lock-screen roster: RobotAuthService.listActiveUsers() reads localUserRepository.listActive(robotId) — purely from the local cache, no network call to PlatformServer needed for this (works even if the VPN is down).
  2. User picks/enters an email; POST /api/hmi-auth/identify → RobotAuthService.identify(email) first checks the local cache; if found and active, returns {status: "has-access", pinSet} immediately. If not found locally, it falls through to platformClient.checkUserExists(email) (a live call to PlatformServer) to distinguish "no PlatformServer account at all" from "account exists but not granted to this robot" — giving a more precise error message either way.
  3. If pinSet is true: POST /api/hmi-auth/login { email, pin } → RobotAuthService.loginWithPin: checks lockedUntil first (too many recent failures → reject without even checking the PIN), then comparePin(pin, user.pinHash) (bcrypt). On failure, localUserRepository.recordFailedAttempt(...) increments a counter and sets a lockout timestamp once PIN_LOGIN_MAX_ATTEMPTS is hit. On success, attempts reset and two JWTs are issued and set as cookies (robotAccessToken scoped to /, robotRefreshToken scoped to /api/hmi-auth only).
  4. If pinSet is false (first time on this robot): the client walks a 3-step OTP flow fully proxied to PlatformServer (RobotServer never generates or checks the OTP/PIN itself) — POST /api/hmi-auth/pin-setup/request-otp, then .../verify-otp (returns a short-lived pinSetupToken), then .../confirm ({pinSetupToken, pin} → platformClient.confirmPinSetup → PlatformServer hashes and stores the PIN, returns the roster entry, which RobotServer immediately caches locally via localUserRepository.applyEntry). The user is not auto-logged-in after this — they must then explicitly log in with the PIN they just set.
  5. Subsequent requests to protected routes carry the robotAccessToken cookie; requireAuth middleware verifies it and populates req.user.
  6. When the access token expires (15 min default), the client calls POST /api/hmi-auth/refresh (reads robotRefreshToken cookie, 24h default) to get a fresh pair without re-entering the PIN.
  7. Separately, PlatformServer can proactively trigger a full roster resync (e.g. right after an admin grants/revokes a user) by calling POST /api/platform-auth/roster/invalidate directly on this robot — mounted with no auth (VPN is the trust boundary) and handled by rosterSyncService.sync().

06 Cross-Component Interaction

RobotServer talks outward to PlatformServer via two independent mechanisms, defined by two small interfaces so either can be swapped for a fake in tests. Locally, it talks to RobotApp only through nginx on the same machine.

1. IPlatformClient / PlatformClient — one-shot REST calls

Every call targets ${PLATFORM_BASE_URL}/api/robot-auth/* and carries two headers: x-robot-id: <this robot's resolved device id> and authorization: Robot <ROBOT_LINK_SECRET>. There is a 25-second request timeout (deliberately generous — these calls now cross the public internet via Cloudflare + nginx, not just localhost), and exactly one automatic retry after a 1.5s pause, but only for a pure network-level failure (DNS/connect failure surfaces in Node's fetch as a TypeError) — a request that got a real HTTP response (even an error one) is never retried. PlatformServer's 4xx responses (bad/expired OTP, unknown user, etc.) are converted to an AppError with the same status code and message, so they pass straight through to the HMI as a meaningful client-facing error rather than being swallowed into a generic 500.

2. IPlatformLink / PlatformLinkClient — persistent outbound WebSocket

Described fully in Flow E. The key architectural point: PlatformServer's notion of "this robot is online" is entirely defined by whether this WebSocket connection is currently open — a push-based fact, not a periodic poll or a VPN-membership guess. The same x-robot-id + Authorization: Robot <secret> scheme authenticates it. Reconnection is automatic and indefinite, with exponential backoff; any disconnection immediately and unconditionally stops the robot's motion as a fail-safe before anything else happens.

Data exchanged: roster entries (RosterEntryDto: assignment id, platform user id, email, name, avatar, PIN hash + metadata) flow PlatformServer → RobotServer via fetchRoster()/roster-invalidate; teleop velocity/estop/release/health frames flow bidirectionally over the robot-link; OTP/PIN-setup tokens flow through PlatformClient's REST calls, with PlatformServer remaining the sole place PINs are ever hashed.

How RobotApp talks to RobotServer

RobotApp is built and served by its own container (RobotApp/Dockerfile, RobotApp/nginx.conf), fronted by nginx, running with network_mode: host alongside RobotServer on the same physical machine. nginx reverse-proxies /api/*, /health, /maps/*, and /ws/* straight through to RobotServer on 127.0.0.1:8000 (RobotServer's own configured PORT), forwarding the Cookie header unchanged. This keeps the browser on a single origin (nginx's), so RobotServer's httpOnly, sameSite: strict session cookies work with zero CORS configuration needed between the two. Authentication for RobotApp is exactly the PIN-login JWT-cookie scheme described in Flow F — there is no separate API key or token RobotApp has to manage itself.

Ports & running without hardware

Default ports: 8000 (HTTP + both WebSocket endpoints, same port, routed by path via WsRouter). In the Docker Compose deployment, RobotServer runs with network_mode: host (shares the host machine's network namespace directly, no port mapping needed) because it must reach the ROS2 graph and other robot services over their native networking.

Running locally without hardware: npm install genuinely needs a sourced ROS2 environment, because rclnodejs compiles native bindings against the installed ROS2 client libraries at install time — this cannot be skipped even for pure unit-test development, though the tests themselves don't need a live ROS2 node once installed. DEV_DEVICE_ID_OVERRIDE lets the server boot and resolve an identity without a physically-attached ESP32 board.

Docker

RobotServer/Dockerfile is built from the repo root as its context (not ./RobotServer), based on ros:lyrical — the distro this repo now consistently targets end-to-end (base image, README, and docs). It's a multi-stage build: a build stage adds build-essential/cmake/python3 (needed to compile rclnodejs's native bindings and tsc-compile the TypeScript) and a lean runtime stage that only copies node_modules + compiled dist/ + package*.json, keeping the final image smaller than the heavy autonav:base image (which bundles nav2-bringup/slam-toolbox/etc. that RobotServer itself never runs — it only talks to those as separate ROS2 nodes over the network).

API docs: interactive, browsable API documentation is available at GET /api/docs whenever the server is running (built from the @openapi JSDoc comments in every *.routes.ts file).

08 Gotchas & Things a New Developer Must Know

Stub rclnodejs call shapes never run against a live ROS2 graph

The three gateway classes cast ROS2 type-name strings through as unknown as rclnodejs.TypeClass<...> to work generically for any topic/service/action (including project-local custom ones like autonav_msgs/srv/SetLedPattern, which rclnodejs's pre-generated type maps don't know about until that package is colcon build'd and sourced). Re-verify field names/shapes on first real build against real hardware.

Stub No TF2 lookup — mapping's waypoint capture will throw

tf2_ros (the ROS2 library for looking up coordinate-frame transforms, e.g. map→base_footprint) isn't confirmed to have an equivalent in rclnodejs. Consequence: getCurrentLocation() is AMCL-only everywhere it's used — and AMCL isn't running during active SLAM mapping. This means MappingService.captureWaypoint() will throw RosUnavailableError for as long as this gap exists, since there's no live pose available during mapping.

Stub FfmpegVideoSource always throws — video streaming doesn't work yet

src/modules/video/ffmpegVideoSource.ts is a stub that always throws. The WebRTC signaling path (video.wsServer.ts) is fully implemented and will attempt to call videoSource.getTrack(), which throws and causes the server to close the viewer's WebSocket with code 1011 and a "not implemented yet" reason — intentional graceful-ish failure, not a crash, but video streaming genuinely does not work yet.

No TODO/FIXME comments exist anywhere in src/

Unfinished work is instead tracked as explicit NotImplementedError (501) stub routes (modules/system/diagnostics, modules/system/maintenance) and the README's "Known gaps" section — a deliberate style choice ("say so honestly instead of lying about it," per a comment in maintenance.routes.ts) rather than silent TODOs.

No direct, inbound teleop endpoint on RobotServer

All remote teleop/control flows exclusively through the one outbound platformLink connection (Flow D). If you're looking for where a browser WebSocket connects straight to RobotServer to drive the robot — it doesn't exist in this codebase; that path was intentionally removed from the old architecture.

/api/system/network/* routes are deliberately NOT behind requireAuth

A robot may need its WiFi configured before anyone can even log in (no internet yet to reach PlatformServer for identity checks). This is an intentional exception to "every operational endpoint requires a logged-in session," not an oversight — but it does mean anyone with network access to RobotServer (same LAN/host) can list/change WiFi and VPN state without authenticating.

Singleton / module-level global state

  • src/ros/rosNode.ts holds the single rclnodejs.Node as a module-level variable, not inside a class instance — calling initRosNode() twice is safe (idempotent, returns the cached node), but getRosNode() throws if called before initRosNode() has completed.
  • src/core/eventBus.ts exports one shared eventBus singleton instance.
  • src/core/wsRouter.ts exports one shared wsRouter singleton instance.
  • src/common/utils/logger.util.ts exports one shared logger singleton.

These are fine for a single-process server with one ROS2 node, but mean you cannot easily run two independent "RobotServer" instances in the same Node.js process (not a real-world concern here, but relevant if anyone tries to unit-test two instances side-by-side).

Constructor-cycle workaround in app.ts

TeleopService needs to know whether Nav2 is actively navigating (so remote teleop doesn't fight it), but NavigationService itself depends on TeleopService (for rotateInPlace, used during the localize flow). Since neither can take the other as a constructor argument without a circular dependency, app.ts constructs both, then calls teleopService.bindNavigationStatus(() => navigationService.getStatus()) afterward to wire the callback in. If you ever need to replicate this pattern elsewhere, this is the established idiom — a post-construction setter, with a doc comment explaining why.

LaunchManager enforces mutual exclusion between Nav2 and SLAM

You cannot launch navigation while mapping is running, or vice versa; attempting to will throw ConflictError (409). This was a direct bug fix over the old server, which had three independent process-tracking globals with no coordination.

The teleop dead-man's switch is per-command, not a fixed-interval watchdog

Each setVelocity call carries its own expiry (ttlMs, default 500ms, but rotateInPlace passes a much longer custom TTL for its own multi-second in-place spin). This lets one long-lived internal call (the localize flow's spin) keep driving the robot unattended for many seconds, while an external remote client's commands still fail safe within half a second if they stop arriving — same mechanism, different deadlines per caller.

PIN hashing happens only on PlatformServer, never on RobotServer

pin.util.ts's doc comment is explicit about this — RobotServer only ever compares a PIN against an already-hashed value it cached from a sync; if you're debugging a PIN-setup issue, the actual hashing logic lives in PlatformServer's codebase, not here.

Revoked local users are never deleted, only status-flagged

MongooseLocalUserRepository.replaceAll marks anyone missing from a fresh roster pull as status: "revoked" rather than removing their document — this preserves failedAttempts/lockedUntil history in case access is re-granted later. If you're querying LocalUserModel directly for any reason, remember stale/revoked rows accumulate rather than disappearing.

The "temp" map name is reserved

Waypoints captured during active SLAM are stored under the map name "temp" (mapping.service.ts's TEMP_MAP_NAME) and later moved (commitWaypoints) onto the real map name once mapping finishes. A map literally named temp by a user would collide with this mechanism.

That's the full reference. For how RobotServer's two PlatformServer channels look from the other side, see the PlatformServer doc; for the touchscreen UI that consumes /ws/topics and the HMI auth routes, see the RobotApp doc.
