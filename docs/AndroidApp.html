1. Purpose & role in the system

AndroidApp is the native Android phone app that lets an AutoNav robot's owner/operator drive their robot remotely, from anywhere with internet access — not just while standing next to it.

Concretely, a signed-in user can:

  • Log in (email/password or Google).
  • Request access to a specific robot (by typing in a robot ID) if they don't have one assigned yet, and wait for an administrator to approve the request.
  • Pick which robot to operate, if they have more than one.
  • See a "is the robot actually reachable and healthy" check before being allowed to drive it.
  • Drive the robot with an on-screen joystick ("teleop" — teleoperation).
  • Hit a big red Emergency Stop ("e-stop") button at any time.
  • Adjust how sensitive the joystick is (a 0–100% speed multiplier).
  • Log out.

Two feature areas are visible placeholders only right now: Analytics (trip history/usage stats) exists as a literal "coming soon" page, and Settings' robot-switcher only appears if the user actually has more than one robot.

Both apps share the same backend (PlatformServer), the same visual brand (same Tailwind color scale, same component naming conventions), and largely the same code patterns (Redux Toolkit Query, React Router, react-hook-form + zod). A developer who knows one can read the other's code structure immediately — only the platform-specific plumbing (native storage, native sign-in, mobile navigation, the teleop feature itself) differs.

The native/mobile layer — Capacitor

Capacitor (@capacitor/core, @capacitor/cli, @capacitor/android) is the framework that turns this web app into an installable Android app. A phone can't "open" a website the way a laptop browser does and call it an app — Capacitor instead creates a real native Android application whose entire UI is one full-screen embedded browser view (a "WebView") that loads the built dist/ web bundle from the device's local storage, not from the internet. From the outside it looks, installs, and behaves exactly like any other Android app — its own icon, its own process, listed in Settings — but internally its screen is just this React app running inside that WebView.

That alone would only get you a glorified bookmark — the WebView's JavaScript can't normally touch Android's camera, secure storage, hardware back button, etc. Capacitor bridges that gap with native plugins: small pieces of actual Android (Java/Kotlin) code, each exposing a JavaScript API, that the WebView's JavaScript can call to reach real device features. This project uses four:

Capacitor.isNativePlatform() (from @capacitor/core) is checked before using any of these, so the exact same code also runs harmlessly in a plain desktop browser during npm run dev — the native calls are simply skipped.

WebSocket (teleop transport)

A WebSocket is a persistent, two-way network connection — unlike a normal HTTP request, which is one request → one response → connection closed. Once opened, either side (the app or PlatformServer) can push a message to the other at any time, with no new connection needed. This is essential for teleop: joystick commands need to stream out continuously and robot status/acknowledgements need to stream back, all in real time. The app uses the browser-standard WebSocket API directly, no extra library, in controlSession.client.ts.

Build-time config

  • .env / .env.example — Vite environment variables (VITE_API_BASE_URL, VITE_WS_BASE_URL, VITE_GOOGLE_WEB_CLIENT_ID), read via import.meta.env.* and baked into the JS bundle at build time — not re-readable at runtime without rebuilding.
  • No Dockerfile exists for this app, unlike RobotServer/RobotApp — this app is distributed as an installed Android APK, not a server container.

4. Architecture layers & patterns

Feature-folder pattern (shared with PlatformApp)

Code is organized by feature, not by technical layer. Instead of one global components/ folder and one global api/ folder for the whole app, each business capability (auth, control, robot-access, robot-select, settings, analytics, home) gets its own folder under src/features/, keeping its own pages/ (full screens), components/ (pieces used only within that feature), its own RTK Query API file, its own types, and its own hooks. src/components/ui/ is the exception — genuinely generic, feature-agnostic building blocks (Button, Card, Input…) live there instead.

This is the exact same convention PlatformApp uses — a developer moving between the two repos recognizes the shape immediately; only the specific features differ (PlatformApp additionally has admin, dashboard, legacy-robot-ui; AndroidApp additionally has control, robot-select).

src/native/ as the bridge layer

src/native/ is this app's one deliberate departure from the pure feature-folder pattern, because it isn't a business feature — it's the seam between ordinary web code and Android-specific capability. Every file in it:

  1. Imports a Capacitor plugin (@capacitor/app, @capacitor/preferences, the Google Sign-In plugin).
  2. Wraps it in a small, app-specific function with a plain-JS-feeling API (readPreference(key), registerBackButtonHandler(router)), usually guarded by Capacitor.isNativePlatform() so the same code is safe to run as a no-op in a plain browser.
  3. Is called from exactly one or two call sites elsewhere in the app (main.tsx for the two "register" functions, tokenStore.ts/RobotSelectionProvider.tsx/VelocitySettingsProvider.tsx for storage, GoogleSignInButton.tsx for sign-in, activeControlSession.ts for background safety).

This keeps every other file in the app ignorant of Capacitor's plugin APIs — if a plugin were ever swapped out, only src/native/* and src/app/tokenStore.ts would need to change.

The control feature's internal structure (the most complex part of this app)

This feature has more internal layering than any other because it manages a stateful, long-lived, safety-critical connection, not a simple request/response API call.

  1. controlSession.protocol.ts — pure data shapes, zero logic. Outbound (ClientFrame): {"type":"joystick","seq":<n>,"data":{"linear":<n>,"angular":<n>}} or {"type":"estop","data":{"engaged":<bool>}} — plain TypeScript interfaces, not validated, because the app only ever sends its own correctly-shaped data. Inbound (ServerFrame, validated with zod as defense-in-depth): {"type":"session","state":"ready"|"robot_offline"|"preempted"|"revoked"}, {"type":"estop_ack","engaged":<bool>}, or {"type":"error","code":<str>,"message":<str>}. Explicitly a hand-kept mirror of PlatformServer's own controlSession.protocol.ts.
  2. controlSession.client.ts — the ControlSessionClient class: the one place that actually owns a raw WebSocket object. Opens the connection (token via the Sec-WebSocket-Protocol subprotocol, not a header or query string — §5g), parses/validates every incoming message against the protocol schema, auto-reconnects with a fixed 2-second backoff up to 5 attempts (but never after a terminal outcome like preempted/revoked, or after an explicit .close()), and exposes send()/sendEstopImmediate()/close(). No knowledge of React at all.
  3. activeControlSession.ts — a tiny module-level variable holding a pointer to "whichever ControlSessionClient is currently live, if any." Exists purely so backgroundSafety.ts — registered once in main.tsx, completely outside any React component — can reach into the live session and fire an e-stop when the app is backgrounded, without prop-drilling the session object through the whole component tree.
  4. useControlSession.ts — the React-facing hook. Creates a ControlSessionClient inside a useEffect whenever (robotId, active) say a session should exist, registers it as "the active session," tears it down (and un-registers it) on cleanup, and exposes React state (status, lastServerFrame) plus two callbacks (sendJoystick, sendEstop).
  5. healthApi.ts — a normal RTK Query endpoint (getRobotHealth), deliberately not part of the WebSocket session at all. A one-shot HTTP health probe, polled on an interval by ControlPage, that must come back healthy: true before a session is even allowed to open.
  6. UI components — HealthGate (shown while unhealthy/checking), JoystickPad (wraps the third-party joystick widget and converts its {x, y} into (linear, angular)), and EstopButton (a big stateful toggle button). None of these three talk to the WebSocket directly — ControlPage.tsx is the only component wiring health + session + joystick + estop together (full flow in §5g).

5. Key flows

(a) Native app boot

Trigger: user taps the AutoNav icon on their phone's home screen.

Participants: Android OS → MainActivity (native) → Capacitor Bridge → WebView → main.tsx → Redux store → router.

(b) Login flow (including native Google Sign-In)

Trigger: user opens the app with no valid session, lands on /login.

Steps — email/password:

  1. LoginForm.tsx validates input against loginFormSchema (zod) via react-hook-form.
  2. On submit, useLoginMutation() calls POST /auth/login through baseApi's fetchBaseQuery (header X-Client: mobile — tells PlatformServer to return tokens in the JSON response body rather than relying only on a cookie, since a Capacitor WebView's cross-origin cookie jar is not something a mobile app can depend on).
  3. authApi.ts's persistTokensAndReturnUser() (shared by signup/login/google) writes the returned {accessToken, refreshToken} into tokenStore as a side effect of RTK Query's transformResponse.
  4. refetchMe().unwrap() is called explicitly — RTK Query's own cache invalidation alone wouldn't re-run getMe here because the pre-login getMe call had already cached a 401 result.
  5. onSuccess() navigates to /.

Steps — native Google Sign-In (this app's version):

  1. GoogleSignInButton.tsx calls ensureGoogleSignInInitialized() (src/native/googleSignIn.ts), which lazily (once) calls the native plugin's GoogleSignIn.initialize({ clientId: VITE_GOOGLE_WEB_CLIENT_ID }).
  2. It then calls GoogleSignIn.signIn() — this invokes Android's native Credential Manager/account-picker UI directly, not a browser popup or redirect. The user picks a Google account already signed into their phone (or signs in natively) and the plugin returns an idToken without the app ever opening a browser tab.
  3. The app sends that idToken to PlatformServer via POST /auth/google/token (useGoogleTokenMutation), which PlatformServer verifies server-side (verifyGoogleIdToken, checking the web client ID as audience — the Android app always uses the web OAuth client ID, never a separate Android one, so the audience check lines up on both apps).
  4. Same persistTokensAndReturnUser + refetchMe + navigate pattern as above.

Contrast with PlatformApp: PlatformApp, running in an ordinary browser, does Google login via a full-page redirect to Google's OAuth consent screen and back — there's no "native credential picker," because a website has no access to the device's native account UI. This app skips that redirect entirely because Capacitor's plugin gives it direct access to Android's own sign-in surface — faster and no page navigation required.

(c) Token storage: why a mobile app needs native secure storage instead of cookies

Context (foundational, not user-triggered): a browser automatically stores Set-Cookie cookies and attaches them to every subsequent request to that domain, with the OS/browser handling encryption-at-rest. A Capacitor WebView embedded inside a native app does not reliably behave the same way — its cookie jar is not something this app's authors chose to depend on. So this app manages its own credentials explicitly.

  • Access token: kept in memory only (a plain JS variable in tokenStore.ts), re-derived via /auth/refresh on every cold start. Never written to disk at all.
  • Refresh token: the one credential that must survive an app restart. Written to @aparajita/capacitor-secure-storage, backed by Android Keystore — hardware/OS-level encrypted storage, specifically chosen because plain localStorage or Capacitor's own Preferences plugin are not encrypted at rest inside a WebView and are unsuitable for a credential.
  • Non-sensitive data (src/native/preferences.ts, used by selected-robot ID and velocity multipliers) deliberately uses the plain, unencrypted @capacitor/preferences plugin instead — real device storage, more durable than WebView localStorage, but with none of Secure Storage's encryption overhead, appropriate since nothing sensitive is stored there.
  • baseApi.ts's baseQueryWithReauth handles token refresh: on any 401, it reads the refresh token out of secure storage, calls POST /auth/refresh with it in the request body (not a cookie), stores the new pair, and retries the original request exactly once — with a "single-flight" guard (refreshInFlight) so concurrent 401s only trigger one refresh call.

(d) Hardware back button + background safety

Hardware back button (src/native/backButton.ts) — trigger: user presses Android's physical/gesture Back button anywhere in the app.

On a native platform, the @capacitor/app plugin's backButton event fires with a canGoBack flag. If canGoBack is true, the app calls router.navigate(-1). If there's nowhere left to go back to, the app calls CapacitorApp.exitApp() and actually closes.

Safety-critical: background e-stop

backgroundSafety.ts fires an immediate e-stop and terminally closes any open control session the instant the app is backgrounded, hidden, or unloaded. This is a real defense against a robot being left in motion — wheels still turning — if the operator backgrounds the app, switches apps, locks their phone, or the app is torn down mid-drive. It is confirmed by the file's own comments and code, not speculative.

Explicitly documented as defense-in-depth: the real safety net is a server/robot-side per-command TTL watchdog (robot-side, ~500ms) that stops the robot on its own if it simply stops receiving commands. This client-side kill switch is just a faster, best-effort reaction on the happy path — the app's own comment is explicit that "safety doesn't depend on" this working. Because this closes the session terminally, ControlPage.tsx separately listens for the app's resume event (and visibilitychange back to "visible") to force a brand-new connection attempt when the user returns to the foreground — otherwise they'd be stuck on "Disconnected" until manually navigating away and back.

(e) Robot selection flow

Trigger: an authenticated user with ≥1 assigned robot reaches the main app shell.

  1. RobotSelectionProvider (wraps the whole app in App.tsx) watches the logged-in user's robot list and, on change, calls readPreference("autonav-selected-robot:<userId>") to look for a previously-remembered choice.
  2. If the stored ID still matches one of the user's current robots, it's used directly.
  3. If nothing valid is stored but the user has exactly one robot, that one is auto-selected and immediately persisted (an unambiguous default, not a guess).
  4. If the user has more than one robot and nothing valid is stored, selectedRobotId stays null on purpose.
  5. RobotRequiredRoute (wraps HomeShell) reads {hasRobot, robots, selectedRobotId, isReady} and redirects: no robot at all → /request-access; not ready yet → spinner; more than one robot and none chosen → /robot-select; otherwise renders the requested page.
  6. RobotSelectPage.tsx lets the user tap a robot card, calling setSelectedRobotId(robotId), which updates state and persists the choice via writePreference, then navigates to /control.

(f) Robot access request flow

Trigger: a logged-in user has zero robots assigned (hasRobot === false).

  1. RobotRequiredRoute redirects to /request-access.
  2. The page loads any existing requests via useListMyRobotAccessRequestsQuery() and shows a RequestStatusBanner for pending/rejected ones.
  3. User types a robot ID and taps "Verify" → useLazyLookupRobotQuery() hits GET /robots/lookup/:robotId. A null result means the ID isn't recognized/available.
  4. If found, and not already pending, the user taps "Request robot access" → useCreateRobotAccessRequestMutation() posts POST /robot-access-requests, which invalidates the RobotAccessRequest RTK Query cache tag so the request list refetches.
  5. The actual approval happens out-of-band by an administrator (via PlatformApp's admin screens, not part of this app) — the user just waits, polling by reopening/reloading this screen.

(g) Core remote-control / teleop flow (end to end) signature feature

Trigger: user navigates to the Control tab (/control) with a robot selected.

Participants: ControlPage → healthApi (HTTP) → useControlSession → ControlSessionClient (WebSocket) → PlatformServer's /ws/control relay → (PlatformServer then relays to RobotServer, outside this app's knowledge) → JoystickPad / EstopButton (UI inputs).

  1. ControlPage.tsx calls useGetRobotHealthQuery(robotId, { pollingInterval: 4000 }) — polls GET /robots/:id/health every 4 seconds, forever (even once connected), so a robot going offline mid-session is still reflected.
  2. While health.healthy !== true, HealthGate.tsx is rendered instead of any controls — "Checking robot status…", "Robot offline" (if checks.link.ok === false, in which case the ROS check is not even meaningful and is hidden), or "Couldn't reach the robot" (hard request error), with a manual "Check again" retry button.
  3. Once health.healthy === true, sessionActive becomes true, and useControlSession(robotId, sessionActive, retrySignal) opens a ControlSessionClient: 
    const url = `${wsBaseUrl}/ws/control?robotId=${robotId}`;
const ws = new WebSocket(url, ["bearer", token]);
    The access token rides the Sec-WebSocket-Protocol subprotocol (["bearer", token]) rather than a header or query string, because a WebSocket handshake can't carry a custom Authorization header and a token must never be put in a URL (logs, proxies, etc. could leak it).
  4. On successful connect, the server is expected to send a session frame ({"type":"session","state":"ready"}). States robot_offline/preempted/revoked are treated as terminal — the client stops auto-reconnecting and shows a dedicated message + manual "Try reconnecting" button (ControlPage's terminalSessionState branch).
  5. Once the session is "open", the UI shows the joystick (JoystickPad) and e-stop (EstopButton) side-by-side, positioned for one-handed thumb reach.
  6. Dragging the joystick: react-joystick-component fires move({x, y}) up to every 100ms (THROTTLE_MS). JoystickPad.handleMove converts stick position to robot velocity: 
    onMove(y, -x); // forward/back -> linear; left/right -> angular (ROS REP-103 sign convention)
  7. ControlPage.handleMove(linear, angular) scales these against both the user's own Settings sensitivity sliders and the robot's real reported velocity envelope from the health check (health.checks.ros.maxLinear/maxAngular — so full stick deflection always maps to this specific robot's actual max speed, not a guessed constant): 
    sendJoystick(linear * linearMultiplier * maxLinear, angular * angularMultiplier * maxAngular);
  8. sendJoystick (from useControlSession) increments a monotonic sequence number and sends: 
    { "type": "joystick", "seq": 7, "data": { "linear": 0.42, "angular": -0.1 } }
  9. Releasing the stick fires onStop → handleStop() → sends {linear: 0, angular: 0}.
  10. Emergency stop: tapping EstopButton calls handleEstopEngage() → sendEstop(true) → {"type":"estop","data":{"engaged":true}}. The button is visually locked into "engaged" state (a hand icon, "Tap to resume") until the server confirms via an estop_ack frame ({"type":"estop_ack","engaged":true}), which ControlPage's effect listens for and syncs into local estopEngaged state — so the UI reflects the server's authoritative state, not just local optimism. Releasing calls sendEstop(false).
  11. Disconnection/reconnection: if the socket drops unexpectedly (not terminal), onclose schedules a reconnect after a fixed 2000ms, up to 5 attempts, then gives up and reports "closed". ControlPage shows this status in a colored badge (live/busy/down tones) with text like "Connecting…", "Reconnecting…", "Disconnected".
  12. Leaving the screen / backgrounding: unmounting ControlPage (e.g. switching tabs) or the OS backgrounding the app (backgroundSafety.ts, flow (d)) both tear the session down via ControlSessionClient.close().

6. Cross-component interaction

  • Base URL / auth: every HTTP call goes through src/app/baseApi.ts's fetchBaseQuery, whose baseUrl is import.meta.env.VITE_API_BASE_URL (e.g. https://platform-server.autonav.in/api). Every request gets an Authorization: Bearer <token> header sourced from tokenStore.getAccessToken(), plus X-Client: mobile so PlatformServer returns fresh tokens in the JSON response body on auth endpoints (not just via Set-Cookie).
  • WebSocket base URL is a separate env var, VITE_WS_BASE_URL (e.g. wss://platform-server.autonav.in), deliberately not derived by string-replacing http→ws on the API URL at runtime, because the API base includes an /api path suffix the WS endpoint does not use.
  • This app never talks to RobotServer directly. Per the README and every control-related comment in the code, all traffic — REST and WebSocket alike — goes to PlatformServer, which (per the system context) is itself the thing that relays teleop sessions between this app and the robot's own RobotServer. From this app's point of view, RobotServer is entirely opaque; the only clue it exists is that RobotHealth.checks.ros and checks.link describe RobotServer/robot-side state that PlatformServer is relaying through.
  • Protocol alignment: controlSession.protocol.ts is explicitly commented as a hand-kept mirror of "PlatformServer's src/modules/control/controlSession.protocol.ts," and control.types.ts's RobotHealth shape is explicitly a mirror of PlatformServer's robotHealth.dto.ts. The frame shapes, state machine (ready/robot_offline/preempted/revoked), and subprotocol-based auth scheme are all consistent with a server deliberately designed to pair with exactly this client.
  • Google OAuth audience: VITE_GOOGLE_WEB_CLIENT_ID must be the same web OAuth client ID PlatformServer's verifyGoogleIdToken checks as the token's audience — this holds even though the sign-in itself happens through Android's native Credential Manager, because a separate Android OAuth client (registered against this app's package name + signing-key SHA-1) only needs to exist in Google Cloud Console to authorize the native sign-in UI; it's never referenced in app code.

7. Running & developing locally + building the Android app

Web-layer development (fastest inner loop)

npm install
cp .env.example .env   # fill in VITE_API_BASE_URL, VITE_WS_BASE_URL, VITE_GOOGLE_WEB_CLIENT_ID
npm run dev             # Vite dev server on port 5190, runnable in a desktop browser

Running via npm run dev in a plain browser works for almost everything except the native-only pieces (Google Sign-In's native picker, secure storage, hardware back button) — those code paths are all guarded to no-op outside Capacitor.isNativePlatform().

Other scripts: npm run build (tsc -b && vite build — type-checks then bundles to dist/), npm run typecheck (tsc -b --noEmit), npm run lint (ESLint over src/**/*.{ts,tsx}), npm run preview (serves the built dist/ locally).

Why building the Android app is a two-step process

Unlike a pure web app, shipping a change here is always two separate steps, because the native Android project ships a copy of the built web bundle inside it (android/app/src/main/assets/public/) rather than loading it live from a server.

  1. Build the web assets: npm run build — produces/updates dist/.
  2. Sync into the native shell: npx cap sync android — copies dist/ into android/app/src/main/assets/public/ and regenerates capacitor.config.json/capacitor.plugins.json inside the native project from capacitor.config.ts and the installed Capacitor plugin packages.

A web-only change (edit a .tsx file) that skips step 2 will not appear in the installed Android app — the old bundle is still sitting inside android/app/src/main/assets/public/ until a sync happens.

Building and installing the APK

npm run build
npx cap sync android
cd android && ./gradlew assembleDebug
# -> android/app/build/outputs/apk/debug/app-debug.apk
adb install -r android/app/build/outputs/apk/debug/app-debug.apk

npx cap run android does build+sync+install+launch in one step onto a connected device/emulator. Live log streaming: adb logcat --pid=$(adb shell pidof -s in.autonav.app) -v time.

Alternatively, android/ can be opened directly in Android Studio (the standard Android IDE) for building/running/debugging the native shell, after the web dist/ has been synced in at least once.

Gradle/JDK requirement: Gradle (the Android build tool) must run under JDK 21 specifically — this is pinned via org.gradle.java.home in android/gradle.properties, independent of whatever Java the invoking shell defaults to, because Android Gradle Plugin 8.x fails outright under newer JDKs (e.g. JDK 25) with Unsupported class file major version 69.

Google Sign-In one-time setup

A native Android OAuth client must be registered in Google Cloud Console (same project as the web client used for VITE_GOOGLE_WEB_CLIENT_ID), bound to this app's package (in.autonav.app) and the signing key's SHA-1 fingerprint:

keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android -keypass android

A second Android OAuth client must be registered for a release-signed build's SHA-1 once that keystore exists. Critically, the clientId actually passed in app code (GoogleSignIn.initialize()) is always the web client ID, never the Android one — the Android client's only job is to exist in Google Cloud Console so the native sign-in flow is authorized.

8. Gotchas & things a new developer must know

Build sync

A code change isn't "live" until synced. Forgetting npx cap sync android after npm run build is the single most common way to think a fix shipped when the installed app is still running the old bundle (§7).

Backgrounding kills the control session — on purpose

backgroundSafety.ts deliberately e-stops and terminally closes any open WebSocket the instant the app is backgrounded/hidden — this is a safety feature, not a bug, but it means switching apps mid-drive (even briefly, e.g. to answer a phone call) always requires reconnecting afterward. ControlPage.tsx has a matching resume/visibilitychange listener that auto-retries the connection when the app comes back to the foreground — if that listener is ever removed or broken, users would get permanently stuck on "Disconnected" until manually leaving and returning to the Control tab. See the full safety callout in §5(d).

The hardware Back button is intentionally rewired

It goes through React Router's history (router.navigate(-1)), not the WebView's native page history. Adding a new route or a new in-app navigation pattern should be checked against this — an unexpected canGoBack value could either trap the user (back does nothing when they expect it to) or exit the app unexpectedly (back exits when they expected in-app navigation).

Only one native permission is declared

Android manifest declares only INTERNET as a permission. No camera, location, storage, or notification permissions are requested — any future feature needing one of those must add it to android/app/src/main/AndroidManifest.xml explicitly.

Network security config is build-variant-specific

android/app/src/main/res/xml/network_security_config.xml (used by release and any build without its own override) blocks all cleartext (plain HTTP) traffic — only HTTPS/WSS is allowed. android/app/src/debug/res/xml/network_security_config.xml overrides this for debug builds to permit cleartext, specifically so local dev against a plain-HTTP LAN backend works. If a debug build is ever suspiciously unable to reach a plain-http:// dev backend, or a release build needs to be checked for not allowing cleartext, these two files are where to look. capacitor.config.ts has matching logic (allowMixedContent, conditionally forcing androidScheme: "http") computed automatically from whether .env's VITE_API_BASE_URL starts with http:// — don't hand-toggle these away from that derivation.

Tokens are never persisted in plain storage

Only the Keystore-backed Secure Storage plugin holds the refresh token; the access token never touches disk at all. Any future feature that touches credentials must go through tokenStore.ts, not through src/native/preferences.ts (which is explicitly documented as "never used for credentials").

Porting a feature from PlatformApp needs real adaptation, not a blind copy

  • PlatformApp's Google sign-in is a browser redirect; this app's is a native Credential Manager call (src/native/googleSignIn.ts + @capawesome/capacitor-google-sign-in). Don't copy PlatformApp's redirect-handling code here.
  • PlatformApp relies on cookies for session identity; this app cannot — it must always carry Authorization: Bearer <token> and the X-Client: mobile header explicitly (baseApi.ts).
  • PlatformApp's dashboard silently defaults to the user's first robot; this app's RobotSelectionProvider/RobotRequiredRoute deliberately never do that once a user has more than one robot, since this app is about to arm a specific physical robot for motion.
  • PlatformApp uses a desktop sidebar; this app uses a bottom tab bar (HomeShell.tsx) — a ported page's navigation chrome needs to be rebuilt, not copy-pasted.
  • This app has no persisted theme toggle (darkMode: "media", follows the OS setting automatically) whereas PlatformApp has its own theme state — don't assume a ThemeProvider exists here.
  • Any UI screen ported over should account for env(safe-area-inset-*) (notches/status bars/gesture bars) — handled globally in src/styles/tailwind.css's body padding and exposed as Tailwind spacing tokens (safe-top/safe-bottom/etc.) in tailwind.config.ts; PlatformApp, being a plain browser page, has no equivalent need.

Placeholder/incomplete features

AnalyticsPlaceholderPage.tsx is a literal "This feature is coming in a future milestone" placeholder — there is no analytics implementation to extend, only a page to replace outright. The Settings page's "Robot"/"Switch robot" card only renders at all when robots.length > 1, so it's easy to miss during single-robot testing.

No TODO/FIXME comments exist in src/

As of this read, the codebase's few caveats are instead documented inline as explanatory comments (e.g. the safety-net framing in backgroundSafety.ts, the hand-synced protocol/DTO mirrors in control.types.ts/controlSession.protocol.ts, and the hand-synced Tailwind brand palette in tailwind.config.ts) — worth reading those comments directly since they record real architectural decisions and known manual-sync obligations rather than being throwaway notes.

Strict TypeScript is on

tsconfig.app.json: strict, noUnusedLocals, noUnusedParameters, noFallthroughCasesInSwitch — npm run build will fail on unused variables/parameters, not just type errors.
