01
Purpose & Role in the System

What it is. RobotApp is a small touchscreen web application ("HMI" — Human-Machine Interface) that lets a person standing physically next to the robot log in and perform a handful of local actions: identify themselves, enter a 4-digit PIN, see whether the robot has internet connectivity, toggle the robot's LED light strip and brightness, and configure Wi-Fi/VPN.

Where it physically runs. It runs on the robot itself, displayed full-screen ("kiosk mode" — a browser running with no address bar, tabs, or window chrome, so it looks like a dedicated appliance screen rather than a web browser) on a touchscreen bolted to the robot. It is built as static HTML/CSS/JavaScript files, served by an Nginx web server (a lightweight program that serves files and forwards network requests — a "reverse proxy") inside a Docker container (a packaged, isolated way of running software) running directly on the robot's onboard computer. A systemd service (deploy/kiosk/robotapp-kiosk.service) launches Google Chrome in app/kiosk mode pointed at this page on boot.

Who uses it. Local operators — people physically standing at the robot — not remote users. It is the equivalent of a payment terminal's screen: whoever is standing there taps through it.

Why it's separate from PlatformApp/AndroidApp. PlatformApp (cloud dashboard) and AndroidApp (mobile) are for remote users anywhere on the internet/VPN, authenticating against PlatformServer with full email+password/Google login, and they never talk to a robot's RobotServer directly — PlatformServer relays everything. RobotApp instead talks directly to the RobotServer process running on the same machine, using a lightweight, robot-local PIN login designed for a shared physical device standing in a warehouse/office, not a personal device. Keeping it a separate codebase/build also means RobotApp's build has no dependency on, and isn't bloated by, PlatformApp's dashboard code.

Design choice

No routing library. There is no React Router or similar — per the README and confirmed in code, navigation between screens is a hand-rolled state machine inside App.tsx using React's useState (a flow/authedView string decides what renders; no URL ever changes). Deliberate, for a small fixed set of kiosk screens rather than a URL-addressable multi-page app.

Design choice

No Redux, no RTK Query, no React Query. Just the browser's native fetch() wrapped in small hand-written client modules (src/api/*.ts) returning Promises, called from useEffect/event handlers, with results kept in local useState. Matches the README: "a handful of screens, not a dashboard."

04
Architecture Layers & Patterns

Feature-based organization vs. type-based

Rather than grouping files by technical type across the whole app (one giant pages/ folder, one giant hooks/ folder), RobotApp groups by feature/domain under src/features/: auth/, home/, settings/. Everything a feature needs — its page components, its own hook (useSession.ts), its own validation schemas (auth.schemas.ts) — lives together in one folder. This keeps related code physically close and easy to find, extend, or delete as a unit, at the cost of some things (like auth.schemas.ts) being specific to that folder rather than globally reusable.

Separate from features, src/components/ui/ holds generic, feature-agnostic building blocks (Button, Card, Input, Spinner, UserAvatar, AppShell) — pure presentation primitives any feature composes together. This is effectively a tiny in-house "design system" layer, duplicated intentionally from PlatformApp (noted in the README) rather than shared as an installable package, so each app's build stays independent.

How pages compose components

A typical "page" component (e.g. IdentifyPage.tsx) is built as:

<AppShell>                      {/* kiosk background + centered card frame */}
  <Card>                        {/* padded content box */}
    <h1>...</h1>
    <form onSubmit={form.handleSubmit(onSubmit)}>
      <Input label="Email" ... {...form.register("email")} />
      <Button type="submit" isLoading={isSubmitting}>Continue</Button>
    </form>
  </Card>
</AppShell>

AppShell and Card provide layout/visual chrome; Input/Button provide styled form controls; the page itself only supplies content, local state (useState), and the submit handler that calls into an src/api/* client.

The API client pattern (src/api/)

Each file is a small object of async functions, one per RobotServer endpoint group, all built on the browser's native fetch():

  • hmiClient.ts → REST, POST/GET to /api/hmi-auth/*. Session-cookie authenticated. Includes a 401-retry-once pattern: a 401 on a non-auth-handshake endpoint triggers one shared /api/hmi-auth/refresh call ("single-flight" — concurrent 401s share one refresh instead of racing to rotate the refresh token) and retries the original request once.
  • firmwareClient.ts → REST, POST to /api/firmware/*. Session-gated. Treats HTTP 502 specially: a well-formed { success: false, message } domain result (e.g. the ESP32 board is disconnected), not a thrown error — so the UI shows it as an inline message instead of crashing.
  • networkClient.ts → REST, GET/POST to /api/system/network/*. Deliberately not authenticated — a robot may need Wi-Fi configured before anyone can log in at all. Also treats 502 as a domain result (e.g. nmcli rejected a connection).
  • topicsSocket.ts → WebSocket, not REST, to /ws/topics. One persistent connection opens lazily on first subscribe and is reused; incoming JSON frames look like { type: string, data: unknown }, fanned out to whichever subscribe(topic, listener) callbacks registered for that type. Reconnects automatically after a fixed 3-second delay if dropped — a kiosk is expected to stay open indefinitely.

All of these assume same-origin deployment (no base URL is hardcoded beyond the path, e.g. fetch("/api/hmi-auth...")) — in production Nginx serves both the static RobotApp files and proxies these API paths to RobotServer, so from the browser's point of view it's all one origin, avoiding CORS and cookie SameSite complications entirely.

05
Key Flows

Flow 1 — App boot sequence

Trigger: device powers on / kiosk Chrome window starts / page is reloaded.

  1. systemd (deploy/kiosk/robotapp-kiosk.service) runs robotapp-kiosk.sh, which waits for the web server to answer, then launches Chrome pointed at the app's URL.
  2. The browser loads index.html, which loads /src/main.tsx as a JS module.
  3. main.tsx calls ReactDOM.createRoot(...).render(<App />) — React takes over the #root <div>.
  4. App.tsx calls the useSession() hook. On mount, useSession immediately calls logout() (see Flow 3) which calls hmiClient.logout() → POST /api/hmi-auth/logout, then sets status = "unauthenticated".
  5. While status === "loading", App.tsx renders <FullPageSpinner /> ("Starting up…").
  6. Once unauthenticated, App.tsx's internal flow state defaults to "picker", so UserPickerPage renders next.

Flow 2 — User identification / PIN login

Trigger: the kiosk lock screen (UserPickerPage) is showing and someone wants to log in.

  1. UserPickerPage calls hmiClient.listUsers() → GET /api/hmi-auth/users on mount, showing the robot's locally cached roster of users who have access to this robot.
  2. (2a) Known user on list: tapping a name calls onPickUser(email, name, pinSet, avatarUrl). In App.tsx this sets flow to "pin-login" if pinSet is true, else "pin-setup".
  3. (2b) Not on list ("+ New user"): flow becomes "identify". IdentifyPage's form calls hmiClient.identify(email) → POST /api/hmi-auth/identify with { email }, returning { status: "has-access" | "no-account" | "no-access", pinSet, name?, avatarUrl? }. "no-account" shows a "create one at autonav.in" message; "no-access" shows a contact-admin message; "has-access" proceeds exactly like step 2a.
  4. PIN login path (PinLoginPage): user types their 4-digit PIN; on submit, hmiClient.login(email, pin) → POST /api/hmi-auth/login with { email, pin }. RobotServer checks it against a locally cached hash — works even if the robot's link to PlatformServer/internet is down, per the README. On success, App.tsx's onLoggedIn calls refresh (from useSession), which re-fetches /api/hmi-auth/session and flips status to "authenticated".
  5. PIN setup path (PinSetupWizard, also used for "Forgot PIN"): on mount it auto-sends an OTP once via hmiClient.requestPinSetupOtp(email) → POST /api/hmi-auth/pin-setup/request-otp, which RobotServer relays to PlatformServer to actually send the email. The user enters the 6-digit code; hmiClient.verifyPinSetupOtp(email, otp) → POST /api/hmi-auth/pin-setup/verify-otp returns a short-lived { pinSetupToken }. The user then chooses and confirms a 4-digit PIN; hmiClient.confirmPinSetup(pinSetupToken, pin) → POST /api/hmi-auth/pin-setup/confirm completes setup and effectively logs them in, after which App.tsx routes to PinLoginPage with a "PIN set — log in with it now" notice.

A subtle but important guard in PinSetupWizard.tsx: the OTP auto-send on mount is wrapped in a useRef boolean (not useState) so it fires exactly once even under React's StrictMode double-invoke in development — otherwise the first emailed code would be silently invalidated by a second, near-simultaneous request before the user could use it.

Flow 3 — Session persistence across reloads (intentionally not persistent)

Trigger: any full page reload/app restart while previously logged in.

  1. useSession()'s useEffect runs logout() unconditionally on every mount — a deliberate design choice (see the comment in useSession.ts), not a bug: "A reload must always ask for the PIN again, even if the session cookie from before the reload is still valid."
  2. This means the only way status becomes "authenticated" is an explicit, interactive PIN submit calling refresh() (Flow 2, step 3) — a stale browser session surviving a reload can never silently re-authenticate someone on a shared kiosk device.
  3. refresh() itself just calls hmiClient.session() → GET /api/hmi-auth/session, which returns { user: SessionUser } if RobotServer's session cookie is currently valid, or throws (caught, setting status = "unauthenticated") if not.

Flow 4 — Live telemetry via WebSocket (topicsSocket.ts)

Trigger: RobotAppHomePage mounts after a successful login.

  1. RobotAppHomePage calls useTopic<RobotStatus>("robotStatus").
  2. Internally, this calls topicsSocket.subscribe("robotStatus", listener), which (a) lazily opens a WebSocket to ws(s)://<host>/ws/topics if not already open, and (b) registers the listener in a Map<topic, Set<listener>>.
  3. RobotServer pushes JSON frames shaped { type: string, data: unknown } over the socket; TopicsSocket parses each frame and dispatches frame.data to every listener registered under frame.type.
  4. For the "robotStatus" topic the payload shape used by this page is { internetConnectivity: boolean }; the hook stores it in component state, re-rendering whenever a new frame arrives.
  5. If the socket closes (network blip, RobotServer restart), TopicsSocket nulls out its reference and schedules a reconnect in 3 seconds — it keeps retrying indefinitely.
  6. The online/offline badge and pulsing status dot on the home screen are purely a reflection of the latest robotStatus frame — there is no REST fallback for this value.

Flow 5 — Settings: LED control

Trigger: a logged-in user opens Settings (SettingsPage) and toggles the light or drags the brightness slider.

  1. Toggling the light calls firmwareClient.setLedPattern(patternId) → POST /api/firmware/led/pattern with body { patternId }, where patternId is LED_PATTERN_IDLE (2) to turn on or LED_PATTERN_OFF (0) to turn off — numeric IDs defined client-side to mirror the firmware's own led_pattern.h header.
  2. Dragging the brightness slider (0–100%) calls firmwareClient.setBrightness(brightness) → POST /api/firmware/led/brightness with the percentage converted to the firmware's native 0–255 range: Math.round((level / 100) * 255).
  3. Both calls return { success: boolean, message: string }. A success: false (e.g. firmware returned 502 because the ESP32 board didn't ACK) is thrown as a regular JS Error and shown inline rather than crashing the page.
  4. There is no "read current state" endpoint, so this page deliberately tracks light-on/brightness optimistically in local useState rather than reading real hardware state back — a reload will reset the displayed toggle/slider to its default even if the light is actually still on.

Flow 6 — Wi-Fi & VPN configuration

Trigger: from the pre-login UserPickerPage ("Wifi settings" button) or the authenticated SettingsPage ("Wifi settings" button) — reachable from both because a robot may need internet configured before anyone can even log in.

  1. On mount, WifiSettingsPage calls networkClient.listWifiNetworks() (GET /api/system/network/wifi → { networks: WifiNetwork[] }, each { ssid, signal, security }) and networkClient.getCurrentWifi() (GET /api/system/network/wifi/current → { connected, ssid? }) in parallel via Promise.all.
  2. Tapping a network in the list opens an inline connect panel; if its security field matches /wpa|wep/i a password field is shown.
  3. Tapping "Connect" calls networkClient.connectWifi(ssid, password) → POST /api/system/network/wifi/connect with { ssid, password }; on success the page re-runs step 1 to refresh the list/current state.
  4. VPN connect/disconnect buttons call networkClient.controlVpn(action) → POST /api/system/network/vpn with { action: "connect" | "disconnect" }.
  5. As with the firmware client, a 502 response is treated as a well-formed { success: false, message } domain failure (e.g. nmcli rejected the connection) rather than a thrown network error.

06
Cross-Component Interaction

  • Talks directly to: RobotServer only, and always same-origin — no base URL/hostname is ever hardcoded in any src/api/*.ts file; every call is a relative path like fetch("/api/hmi-auth/session") or new WebSocket(protocol + "://" + window.location.host + "/ws/topics").
  • In development: vite.config.ts's dev server runs on port 5174 and proxies any request to /api to http://localhost:8000 (where RobotServer is expected to run locally). The WebSocket path (/ws) is not in the dev proxy config, so live topic data won't work against a local dev server unless RobotServer is reachable and proxying is set up separately — a potential dev-environment gap (see Gotchas).
  • In production: RobotApp's static build is served by Nginx (nginx.conf) inside a Docker container running with network_mode: host (the container shares the robot's actual network interfaces), so 127.0.0.1:8000 inside the container is the host's own loopback, where RobotServer listens. Nginx reverse-proxies /api/, /health, /maps/, and /ws/ (with WebSocket upgrade headers) to that address, forwarding the Cookie header explicitly. Everything else falls through to serving the static built files, with an SPA fallback (try_files $uri $uri/ /index.html) for any unmatched path.
  • Auth mechanism: an HTTP-only session cookie issued by RobotServer (RobotServer/src/modules/robot-auth/robotAuth.service.ts). Because the browser always sees RobotApp and RobotServer as the exact same origin, there is no CORS configuration and no SameSite/cross-site cookie handling needed anywhere in this app — repeatedly called out in code comments (hmiClient.ts, nginx.conf, the README).
  • Does NOT talk to PlatformServer directly, confirmed both by the README ("PlatformApp ... never talks to a robot directly ... RobotApp is the thing that does talk to RobotServer directly") and by the complete absence of any PlatformServer URL/hostname anywhere in RobotApp/src. When OTP emails need sending (PIN-setup flow), the request goes RobotApp → RobotServer → (RobotServer's own platformClient.ts) → PlatformServer; RobotApp itself only ever sees RobotServer's /api/hmi-auth/* surface.

Running & Developing Locally

npm scripts

npm run dev          # starts Vite dev server on port 5174 (strictPort: true — fails rather than picking another port)
npm run build         # tsc -b (type-check only, no JS emitted) then `vite build` → produces dist/
npm run preview       # serves the built dist/ locally for a production-like smoke test
npm run lint          # ESLint over src/**/*.{ts,tsx}
npm run test          # vitest run — runs the test suite once
npm run test:watch    # vitest — reruns tests on file change

Dev server details

Port 5174 (fixed, per vite.config.ts's server.strictPort: true), with /api/* requests proxied to http://localhost:8000 — so to develop against live data you need RobotServer running locally on port 8000 at the same time. No .env file or environment variables are used anywhere in this app (no src/config or import.meta.env usage was found) — all such configuration (base URLs, ports) is either a relative path or hardcoded directly in vite.config.ts/nginx.conf.

Docker / Nginx deployment

  1. RobotApp/Dockerfile (built from the repo root as its context — note the COPY RobotApp/... paths, matching docker-compose.yml's dockerfile: RobotApp/Dockerfile with context: .) does a two-stage build: a node:20-slim stage runs npm ci and npm run build, producing /robotapp/dist; a second nginx:1.27-alpine stage copies that dist/ into Nginx's web root and copies in the custom nginx.conf, exposing port 80.
  2. docker-compose.yml's robotapp service builds this image, runs with network_mode: host (so Nginx's port 80 is directly the robot's own port 80, no Docker port-mapping needed — required so the 127.0.0.1:8000 proxy target inside nginx.conf really is RobotServer's host-level port), and depends on the robotserver service starting first.
  3. For the kiosk screen itself: deploy/kiosk/robotapp-kiosk.service is a systemd unit that launches deploy/kiosk/robotapp-kiosk.sh on graphical login; that script polls the app's URL until it responds, then opens Google Chrome in --app= mode (no browser chrome) and forces true fullscreen via a simulated F11 keypress using xdotool.
# Build the image from the repo root
docker compose build robotapp

# Run the full stack (robotserver first, then robotapp)
docker compose up robotserver robotapp

Building for the kiosk device: build the Docker image (docker compose build robotapp from the repo root, or as part of a full docker compose up), deploy/run it on the robot's onboard computer with the existing docker-compose.yml, and ensure the systemd kiosk service/script are installed so Chrome auto-launches against it on boot.

Gotchas & Things a New Developer Must Know

Two of the items below are real bugs worth fixing. The rest are deliberate design choices that look like bugs at first glance — don't "fix" them.

Bug — fix before relying on it

The kiosk launcher script points at port 5174, not port 80. deploy/kiosk/robotapp-kiosk.sh has URL="http://localhost:5174/" active, with a commented-out # URL="http://localhost/" right above it. Port 5174 is the Vite dev server port, while the production Docker/Nginx stack (docker-compose.yml, network_mode: host) serves on port 80. As committed, the kiosk script would only work if a dev server happens to be running — confirm/fix this before relying on it against a docker compose up deployment.

Bug — dev-environment gap

The dev-server proxy only covers /api, not /ws. vite.config.ts's proxy config only forwards /api to localhost:8000; topicsSocket.ts connects to /ws/topics on window.location.host, which during npm run dev would be the Vite dev server (port 5174) itself, not RobotServer — so live telemetry (the online/offline badge on the home screen) will not work against npm run dev without either adding a /ws proxy entry or testing against the full Docker/Nginx stack instead.

By design, not a bug

Kiosk-mode fixed viewport. index.html's viewport meta tag and tailwind.css both hardcode a 1280×800 layout (width: 1280px; height: 800px; overflow: hidden on html/body/#root) — this app is not responsive and is not meant to be; it assumes one specific touchscreen resolution. Changing target hardware would require revisiting these fixed dimensions.

By design, not a bug

Every reload forces re-login, on purpose. useSession.ts calls logout() unconditionally on mount even if a still-valid session cookie exists — this is not a bug to "fix" by skipping it; removing it would let anyone who reloads the kiosk screen inherit the previous operator's session.

By design, not a bug

Optimistic LED state, no read-back. SettingsPage.tsx's LED toggle/brightness slider are optimistic, client-side-only state — there's no GET endpoint for current LED state, so a page reload resets the displayed UI regardless of the light's actual physical state.

By design, not a bug

502 used as a valid domain response. Both firmwareClient.ts and networkClient.ts treat HTTP 502 specially — unwrapping it as a normal { success: false, message } payload instead of throwing — because RobotServer uses 502 to mean "the downstream hardware/system command failed," not "the gateway failed." Any new endpoint following this convention needs the same handling; don't assume all non-2xx statuses are fatal in this API layer.

Touch-only, no browser chrome

user-select: none and overscroll-behavior: none are set globally in tailwind.css specifically to prevent accidental text selection and pull-to-refresh gestures on a touchscreen kiosk. There's no keyboard-first design consideration; everything is tap targets.

The PIN model is shared-device security, not personal-device security

A 4-digit PIN is weak compared to PlatformApp's password/Google login, but that's by design: this device sits in a public/shared physical location, identity is pre-vetted by RobotServer's roster sync from PlatformServer, and the PIN only needs to gate who on that pre-approved list is currently operating the robot — not prove identity to the internet at large. Don't try to "harden" this into a full auth system without understanding that trade-off is deliberate (see README).

No routing library

Flow state lives entirely in App.tsx's component state. Adding a new screen means extending the UnauthFlow/AuthedView union types and the if/else chain in App.tsx, not adding a route. There is no browser back-button support or deep-linkable URLs for individual screens.

UI primitives duplicated from PlatformApp

Confirmed in the README — not shared via a common package. If asked to "share" Button/Card/Input with PlatformApp, that's a conscious architectural trade-off (independent builds) that needs deliberate revisiting, not an oversight to silently fix.

Test coverage is minimal

App.test.tsx has exactly two integration tests (no-session → picker screen; new-user → PIN-setup wizard), using a hand-mocked fetch. There's no test coverage at all for the settings/Wi-Fi/firmware/WebSocket flows — a new developer adding features there currently has no existing test pattern beyond App.test.tsx's fetch-mocking style to imitate.

No TODO/FIXME comments anywhere in RobotApp/src

The explanatory comments present (e.g. in useSession.ts, PinSetupWizard.tsx, hmiClient.ts) are intentional design-rationale notes, not markers of unfinished work. The RobotAppHomePage.tsx "Teleop, navigation & mapping controls land here in a future milestone" box is the one explicit placeholder for planned-but-not-yet-built functionality.
