01 Purpose & Role in the System

PlatformApp is the web "operator dashboard" for AutoNav — a website (not an app you install) that regular users and admins open in a browser to:

  • Sign up / log in (email+password, or "Continue with Google")
  • Request access to a specific robot (by typing in a robot ID printed on the robot)
  • See which robot(s) they've been granted, and switch between robots if they have more than one
  • (Admins only) approve/reject pending access requests, provision new robots, and manage which users are linked to which robots
  • (Future) operate/monitor a robot — mapping, navigation, analytics, documentation — these screens currently exist only as "coming soon" placeholders (see Section 08)

It is one of five Node.js/TypeScript sub-projects in AutoNav. Concretely:

  • PlatformApp never talks to a robot directly. It only ever calls PlatformServer (the cloud/VPN backend) over HTTPS. PlatformServer is the single source of truth for accounts, the robot fleet registry, auth, and approval workflows, and it's also the component that would broker any live robot data to a browser in the future.
  • A robot's own local touchscreen UI is a different app (RobotApp), served by that robot's own on-board RobotServer — PlatformApp has no code path to it.
  • AndroidApp is a sibling mobile client that shares many of the same patterns (feature folders, RTK Query, Zod schemas) but is a separate Capacitor-wrapped app, not part of PlatformApp.

In short: PlatformApp is the "front door + fleet admin console" of AutoNav, PlatformServer is its only backend, and actual robot control/telemetry is explicitly out of scope today (per the README: "it never calls a robot's RobotServer directly").

02 Tech Stack Explained

Plain-English explanations come first, followed by exactly how/where AutoNav uses the package.

React / React DOM

A library for building UIs out of reusable "components" — JavaScript functions that return a description of some HTML. The UI re-renders automatically whenever the data it depends on changes, instead of you manually editing the DOM.

The entire UI (every .tsx file in src/) is built as React components. src/main.tsx mounts the root component into the page's <div id="root">.

TypeScript

A superset of JavaScript that adds optional type annotations ("this function takes a string and returns a number") checked before the code runs, catching a large class of bugs at build/edit time instead of in the browser.

Every source file is .ts/.tsx. Types live in files like auth.types.ts. npm run build runs tsc -b first, so type errors fail the build.

Vite

A fast frontend build tool/dev server. It serves source files to the browser almost instantly during development and produces an optimized production bundle for deployment.

Configured in vite.config.ts. npm run dev starts the dev server (port 5175 — see the doc-drift gotcha). This project was migrated off Create React App, which is unmaintained.

React Router

Maps URL paths (/login, /admin/users) to which React component should be shown, without a full page reload — a "single-page app" router.

src/router/index.tsx defines the whole route tree via createBrowserRouter. "Route guard" wrapper components (Section 04) decide whether a route is actually allowed to render.

Redux Toolkit & RTK Query — the part most worth slowing down for

Redux is a pattern for holding an app's shared state in one central, predictable "store" object, updated only through well-defined actions, instead of scattering state across many components. Redux Toolkit (RTK) is the modern, boilerplate-reduced way to write Redux. In this app the store holds almost nothing except the RTK Query cache below — there is deliberately no hand-written slice for "current user," because that would risk going out of sync (see Gotcha 6).

RTK Query is a data-fetching layer built on top of Redux specifically for talking to a backend API. Instead of manually calling fetch() and writing useState/useEffect to track loading/error/data yourself, you declare "endpoints" once and RTK Query gives you a React hook (e.g. useGetMeQuery()) that automatically fetches, caches, de-duplicates concurrent requests, and refetches when told to.

"Slice"

src/app/baseApi.ts defines the shared baseApi — the one RTK Query "base" that every feature attaches to. Each feature then calls baseApi.injectEndpoints(...) to add its own piece: authApi.ts, adminApi.ts, robotAccessApi.ts. Think of a slice as "this feature's own corner of the shared API client."

Queries vs. mutations

A query reads data — getMe, listAllRobots. A mutation writes data — login, approveRequest, createRobot. Queries auto-fetch on mount; mutations you trigger yourself (on submit, on click).

Cache invalidation

An endpoint can be tagged (e.g. "Me"), and a mutation can declare invalidatesTags: ["Me"] — "anything cached under tag Me is now stale, refetch it." Approving a request invalidates AdminRobotAccessRequests and AdminRobots so both admin lists refresh themselves automatically.

Why RTK Query over plain fetch: it removes the need for manual loading/error state and de-dupes identical in-flight requests — and, critically here, useAuth() (src/features/auth/useAuth.ts) treats RTK Query's cache for GET /users/me as the single source of truth for "who is logged in," rather than duplicating that into a separate Redux slice that could drift out of sync after login/logout/refresh.

Zod + React Hook Form

Zod is a schema/validation library: you describe the "shape" a piece of data must have (e.g. "email must be valid, password ≥ 8 chars"), and Zod both validates data at runtime and lets TypeScript infer a matching type automatically, so the rule and the type can't drift apart. React Hook Form manages form field values, touched/dirty state, and validation errors efficiently; @hookform/resolvers is the small adapter that lets it use a Zod schema as its validation rules.

Every form has a matching *.schemas.ts file (auth.schemas.ts, admin.schemas.ts), explicitly commented as mirroring PlatformServer's own validation. Every form component calls useForm({ resolver: zodResolver(someSchema) }) then spreads register("fieldName") onto each input — this replaced earlier manual useState wiring.

Tailwind CSS

A "utility-first" CSS framework: instead of writing custom CSS classes, you compose a look directly in markup from small pre-defined classes like flex, rounded-xl, dark:bg-slate-900.

tailwind.config.ts defines a custom brand palette and the Inter font, and sets darkMode: "class" (toggled by a class on <html>, not just OS preference). Virtually every component's className is Tailwind utilities.

Theming system (src/app/theme/)

  • theme.context.ts defines a React Context (ThemeContext) — a mechanism for sharing a value ({ theme, toggleTheme }) with any descendant component without manually passing it down through every layer of props ("prop drilling").
  • ThemeProvider.tsx actually owns the theme state: initializes from localStorage (falling back to OS prefers-color-scheme), toggles the dark class on <html> (which Tailwind's darkMode: "class" reads), and persists the choice back to localStorage on every change.
  • index.html contains a small inline <script> that runs before React even loads, reading the same key and adding the dark class immediately — avoiding a "flash of the wrong theme" on first paint.
  • src/components/ui/ThemeToggle.tsx is the sun/moon button that calls toggleTheme().

03 Architecture Layers & Patterns

Feature-folder pattern

Instead of organizing code by type (all API calls in one giant folder, all components in another), this app organizes by feature — a self-contained slice of functionality. Each feature folder under src/features/<name>/ typically contains an API slice, type definitions, Zod schemas, components, and pages. This keeps everything related to "robot access requests," for instance, in one place rather than spread across generic api/, types/, components/ folders — a new developer working on one feature rarely needs to touch another feature's files.

Route-guarding pattern

React Router (src/router/index.tsx) renders a tree of routes, but several routes need to be conditionally allowed based on who is logged in and what state they're in. This is done with small wrapper components ("guards") that each call useAuth() and either render their children or redirect elsewhere via React Router's <Navigate>:

// src/router/ProtectedRoute.tsx
export function ProtectedRoute({ children }: PropsWithChildren) {
  const { status } = useAuth();
  if (status === "loading") return <FullPageSpinner />;
  if (status === "unauthenticated") return <Navigate to="/login" replace />;
  return <>{children}</>;
}

The four guards, composed from simplest to most specific:

  • PublicRoute — for /login, /signup, /forgot-password: if you're already authenticated, bounce you to / instead of showing the login form again.
  • ProtectedRoute — the base guard: must be authenticated, else bounce to /login.
  • AdminRoute — wraps ProtectedRoute, additionally requires isAdmin, else bounce to /. Used for /admin/requests, /admin/users, /admin/robots.
  • RobotRequiredRoute — wraps ProtectedRoute, additionally requires hasRobot unless the user isAdmin, else bounce to /request-access. This wraps the entire dashboard shell.

All four derive their decision from the same useAuth() hook, so there is one consistent definition of "logged in," "admin," and "has a robot" used everywhere.

"Robot selection" context

A single user can be granted access to more than one robot (CurrentUser.robots[] — changed from a single CurrentUser.robot specifically to support that). Once inside the dashboard, most screens (and, eventually, any robot-specific API calls) need to know which one of the user's robots is currently "in focus":

  • RobotSelectionContext holds { selectedRobotId, setSelectedRobotId }.
  • RobotSelectionProvider wraps the dashboard and: reads the user's robot list from useAuth(); restores a previously-chosen robot from localStorage (keyed per-user-id); falls back to the first robot if the stored choice is no longer valid (e.g. access was revoked); exposes setSelectedRobotId(), persisting back to localStorage.
  • useSelectedRobot() is the hook components actually use — it resolves the raw id into the full robot object.
  • Consumers: Topbar.tsx (the switcher dropdown, 2+ robots only), MappingPlaceholderPage.tsx and NavigationPlaceholderPage.tsx (show the selected robot's name — a hint for how future robot-specific screens would scope themselves).

This is the mechanism by which an eventual "Mapping" or "Navigation" screen would know which robot's data/control to request — without it, a multi-robot user would have no way to disambiguate.

04 Key Flows

(a) App boot & auth hydration

Trigger: browser loads the page, any URL.

  1. index.html's inline <script> runs synchronously, reading localStorage["autonav-theme"] and adding the dark class to <html> if needed (avoids a theme flash).
  2. src/main.tsx renders <Provider store={store}><App /></Provider> into #root.
  3. App.tsx renders <ThemeProvider><RouterProvider router={router} /></ThemeProvider> — ThemeProvider re-derives/owns theme state; RouterProvider starts matching the current URL against src/router/index.tsx.
  4. Whichever route matches wraps its page in a guard (e.g. ProtectedRoute), which calls useAuth() → useGetMeQuery() → fires GET /users/me against PlatformServer (cookie-based, Section 06).
  5. While in flight, status === "loading" shows a FullPageSpinner. Once resolved, the guard either renders the real page or redirects — this is "auth state hydration."

(b) Signup flow

Trigger: user submits the signup form on /signup.

  1. SignupPage.tsx renders <SignupForm onSuccess={() => navigate("/")} /> inside AuthShell/Card.
  2. SignupForm.tsx uses useForm({ resolver: zodResolver(signupFormSchema) }); on submit, validates first (name 1–100 chars, valid email, password ≥ 8 chars) — if invalid, errors render inline and nothing is sent.
  3. On valid submit, signup(values).unwrap() fires POST /auth/signup with SignupRequest. Tagged invalidatesTags: ["Me"].
  4. Response is transformed from { user: CurrentUser } to just CurrentUser.
  5. Because the pre-signup getMe() cache entry was a cached 401 (invalidating a tag doesn't retrigger a query that's errored/cached-401 the same way), the form explicitly calls await refetchMe().unwrap() before calling onSuccess().
  6. onSuccess() calls navigate("/"), where RobotRequiredRoute decides (based on the now-populated hasRobot) whether to show the dashboard or redirect to /request-access (a brand-new signup has no robots yet).
interface SignupRequest {
  email: string;    // valid email
  password: string; // ≥ 8 chars
  name: string;     // 1–100 chars
}

(c) Login flow, including Google OAuth

Trigger: user submits the login form, or clicks "Continue with Google," on /login.

Steps (password)

  1. LoginForm validates with loginFormSchema (email, non-empty password).
  2. login(values).unwrap() → POST /auth/login with LoginRequest { email, password }; mutation tagged invalidatesTags: ["Me"].
  3. Same refetchMe() pattern as signup, then navigate("/").
  4. Any error (wrong password, etc.) surfaces via the mutation's error field through getApiErrorMessage(error).

Steps (Google)

  1. GoogleAuthButton is literally <a href={googleLoginUrl()}> — googleLoginUrl() returns ${'{'}VITE_API_BASE_URL{'}'}/auth/google. Clicking it is a full page navigation, not a fetch — the browser leaves the SPA entirely and goes to PlatformServer, which redirects to Google, handles the OAuth callback itself, sets the auth cookies, and 302-redirects back to PlatformApp's /auth/callback.
  2. OAuthCallbackPage.tsx mounts, immediately calls refetch() on getMe, and on success navigates to /, or to /login on failure.

(d) Forgot/reset password flow

Trigger: user clicks "Forgot password?" on /login.

  1. Step "email": forgotPasswordFormSchema validates the email; forgotPassword({ email }) → POST /auth/forgot-password. On success, moves to step "otp" (the response is intentionally vague — "if an account exists…" — so the UI can't be used to enumerate registered emails).
  2. Step "otp": verifyOtpFormSchema validates a 6-digit code; verifyOtp({ email, otp }) → POST /auth/verify-otp, which returns { resetToken: string } — a short-lived token proving the OTP was correct, stored only in component state (not persisted). Moves to step "reset".
  3. Step "reset": resetPasswordFormSchema validates newPassword (≥ 8 chars) and that it matches confirmPassword; resetPassword({ resetToken, newPassword }) → POST /auth/reset-password. Moves to step "done," which tells the user they've been "logged out everywhere" and links back to /login.
  4. A useRef guard (isSendingOtpRef) prevents a double-click from firing two OTP emails before RTK Query's isLoading flag has re-rendered — a deliberate workaround since isLoading only updates on the next render.
forgotPasswordFormSchema: { email: string }
verifyOtpFormSchema:     { email: string; otp: string /* 6 digits */ }
  // → POST /auth/verify-otp  ⇒  { resetToken: string }
resetPasswordFormSchema: {
  newPassword: string;     // ≥ 8 chars
  confirmPassword: string; // must match newPassword
}
  // → POST /auth/reset-password { resetToken, newPassword }

(e) Robot access request flow

Trigger: a logged-in, robot-less, non-admin user is redirected to /request-access by RobotRequiredRoute.

  1. Page loads useListMyRobotAccessRequestsQuery() (GET /robot-access-requests/mine) to show any existing pending/rejected requests via RequestStatusBanner.
  2. User types a robot ID (the physical ID printed on the robot) and clicks "Verify" → useLazyLookupRobotQuery() fires GET /robots/lookup/:robotId on demand (a "lazy" query is one you trigger imperatively rather than automatically on mount). Returns a minimal, non-admin-safe RobotOption or null.
  3. If found and not already pending, clicking "Request robot access" calls createRobotAccessRequest({ robotId: foundRobot.id }) → POST /robot-access-requests, tagged invalidatesTags: ["RobotAccessRequest"], which refreshes the "mine" list to show the new pending request.
  4. The request now sits as status: "pending" until an admin acts on it (flow f1).
  5. RobotRequiredRoute won't let the user into the dashboard until an admin approves a request and getMe's cache is refreshed (login/refetch) to reflect the new robots[] entry.
interface RobotOption {
  id: string;
  robotId: string;
  name: string;
  displayName?: string;
}
// GET /robots/lookup/:robotId  ⇒  RobotOption | null
// POST /robot-access-requests { robotId: foundRobot.id }

(f1) Admin workflow — approving a request

Trigger: an admin visits /admin/requests (gated by AdminRoute).

  1. AdminRequestsPage.tsx loads useListPendingRequestsQuery() (GET /admin/robot-access-requests?status=pending) and renders RequestsTable.
  2. Clicking "Approve" opens ApproveRequestDialog, pre-populated with the robot the user originally requested (defaulted from request.robot?.id), but overridable via a <select> populated from useListAllRobotsQuery() (excluding "retired" robots).
  3. Confirming calls approveRequest({ id, robotId }) → POST /admin/robot-access-requests/:id/approve, tagged invalidatesTags: ["AdminRobotAccessRequests", "AdminRobots"] — both the pending-requests list and the robots list refresh.
  4. Clicking "Reject" directly calls rejectRequest({ id, reason? }) → POST /admin/robot-access-requests/:id/reject (no dialog).
// POST /admin/robot-access-requests/:id/approve  { id, robotId }
//   invalidatesTags: ["AdminRobotAccessRequests", "AdminRobots"]
// POST /admin/robot-access-requests/:id/reject   { id, reason? }

(f2) Admin workflow — robot & user management

Trigger: an admin visits /admin/robots or /admin/users (gated by AdminRoute).

Managing robots

  1. AdminRobotsPage.tsx shows AddRobotForm + RobotsList side by side.
  2. AddRobotForm validates with createRobotFormSchema (robotId: 3–32 chars, letters/digits/hyphens only; name; vpnHostname; optional displayName), then createRobot(values) → POST /admin/robots, tagged invalidatesTags: ["AdminRobots"]. On success, shows the created robot's info — the current code says "no secret to copy": the robot authenticates to PlatformServer using its own device id matching robotId, not a generated secret shown here.
  3. RobotsList shows useListAllRobotsQuery() with status badges (provisioned/active/retired), a "Manage users" button opening ManageRobotUsersDialog, and a "Delete" button (deleteRobot, with a window.confirm guard, tagged to invalidate AdminRobots, AdminUsers, RobotOptions).

Managing user ↔ robot assignments

(many-to-many, reflected in two dialog components covering the same underlying RobotAssignment relation from each side)

  1. ManageRobotUsersDialog (opened from RobotsList, robot-centric) and ManageUserRobotsDialog (opened from UsersTable, user-centric) both list current active assignments (useListAssignmentsForRobotQuery/useListAssignmentsForUserQuery) and let the admin grant a new one (grantRobotAssignment({ userId, robotId, hmiAccess, platformAccess }) → POST /admin/robot-assignments) or revoke one (revokeRobotAssignment({ id }) → POST /admin/robot-assignments/:id/revoke).
  2. Each assignment carries two independent boolean flags, toggled live via updateRobotAssignmentAccess (PATCH /admin/robot-assignments/:id/access): hmiAccess — can log into that robot's own on-device RobotApp kiosk (PIN login); platformAccess — shows up in that user's "my robots" list here in PlatformApp.
  3. AdminUsersPage.tsx/UsersTable.tsx additionally lets an admin promote/demote a user's role (updateUserRole → PATCH /admin/users/:id/role) and delete a user (deleteUser → DELETE /admin/users/:id), both disabled for the admin's own account (isSelf check) to prevent self-lockout.
interface CreateRobotRequest {
  robotId: string;     // 3–32 chars, letters/digits/hyphens only
  name: string;
  vpnHostname: string;
  displayName?: string;
}
interface RobotAssignment {
  userId: string;
  robotId: string;
  hmiAccess: boolean;      // robot's own on-device kiosk login
  platformAccess: boolean; // shows up in "my robots" in PlatformApp
}

(g) Dashboard / robot-selection flow

Trigger: a robot-having user (or an admin) lands on / after RobotRequiredRoute passes.

  1. DashboardLayout.tsx wraps Sidebar + Topbar + the routed child (<Outlet>) inside RobotSelectionProvider.
  2. RobotSelectionProvider reads user.robots from useAuth(); if the user has exactly one robot, there's effectively nothing to choose; if they have multiple, it restores the last choice from localStorage (or defaults to the first robot).
  3. Topbar.tsx renders either plain text (0 or 1 robot) or a <select> dropdown (2+ robots) wired to setSelectedRobotId.
  4. DashboardHome.tsx lists all of the user's robots (not just the selected one) with online/offline badges (robot.status === "online").
  5. MappingPlaceholderPage/NavigationPlaceholderPage call useSelectedRobot() and display the selected robot's name — demonstrating the intended pattern: once mapping/navigation are real features, they'd scope their API calls (likely proxied through PlatformServer) to selectedRobot.id/vpnHostname. This proxying/scoping is not implemented yet — see Sections 06 and 08.

05 Cross-Component Interaction

Base URL / API client configuration

  • src/app/baseApi.ts creates fetchBaseQuery({ baseUrl: import.meta.env.VITE_API_BASE_URL, credentials: "include" }). fetchBaseQuery is RTK Query's thin wrapper around the browser's native fetch.
  • VITE_API_BASE_URL is a Vite environment variable (prefixed VITE_ so Vite exposes it to client code) — e.g. .env.example sets it to http://localhost:4000/api for local dev against a locally-run PlatformServer; .env.local points it at https://platform-server.autonav.in/api, the public API domain, so the app works correctly even when loaded through the EC2 nginx dev reverse-proxy rather than straight localhost.
  • In production, PlatformApp is a static build served from its own domain (dashboard.autonav.in) while PlatformServer's API lives on a separate subdomain (platform-server.autonav.in) — cross-origin, hence credentials: "include" being essential and presumably CORS configured server-side.

Auth token storage / attachment

  • Tokens are never touched by JavaScript in this app. credentials: "include" tells fetch to send cookies with every cross-origin request; PlatformServer issues the access/refresh JWTs as httpOnly cookies (cookies JavaScript cannot read), so there is no localStorage/sessionStorage token to manage or leak via XSS.
  • apiError.ts's helper logic only ever deals with error messages from response bodies, never tokens.

Silent refresh on 401

const baseQueryWithReauth: BaseQueryFn<...> = async (args, api, extraOptions) => {
  let result = await rawBaseQuery(args, api, extraOptions);
  if (result.error?.status === 401) {
    refreshInFlight ??= refreshAccessToken(api, extraOptions).finally(() => { refreshInFlight = null; });
    const refreshed = await refreshInFlight;
    if (refreshed) result = await rawBaseQuery(args, api, extraOptions);
  }
  return result;
};

When any request gets a 401, this wrapper calls POST /auth/refresh exactly once even if several requests 401 concurrently (the module-level refreshInFlight promise is shared), then retries the original request(s) if the refresh succeeded. This is the only place in the frontend that needs to know a refresh mechanism exists — per the source comment: "The frontend never reads the JWTs themselves."

Remote-control / live video / teleop

Not implemented in PlatformApp today. There is no WebSocket client code anywhere in src/ (outside the untouched legacy-robot-ui, which used a raw ws:// URL to talk directly to a robot — an abandoned approach). The README is explicit: "Live ROS telemetry/control, if ever surfaced here, would be proxied through PlatformServer … not fetched client-side." The MappingPlaceholderPage/NavigationPlaceholderPage components and their useSelectedRobot() usage are essentially the scaffolding for where that would plug in later (you'd know which robot to target), but the actual data channel doesn't exist yet in this codebase. AndroidApp, PlatformServer's sibling mobile client, is ahead of PlatformApp here: it already has the joystick/teleop control feature implemented.

Doc-drift: the dev server port

The README's "Getting started" snippet says http://localhost:5173 (Vite's default). vite.config.ts actually configures port 5175. Copy-pasting from the README will silently point you at nothing.

Dev server details (vite.config.ts)

  • Listens on port 5175 (not Vite's usual 5173).
  • host: true plus allowedHosts: ["dashboard.autonav.in"] lets the project's EC2 nginx dev reverse-proxy forward Host: dashboard.autonav.in traffic to this local dev server over the VPN. This only affects vite dev; the production container serves a static build instead (no dev server involved).
  • Test config lives in the same file's test block: environment: "jsdom", globals: true (so describe/it/expect don't need importing), setupFiles: "./src/test/setup.ts", css: true, and excludes src/legacy-robot-ui (plus the usual node_modules/dist).

Tests

LoginForm.test.tsx is the only test suite present. It uses renderWithProviders (fresh Redux store + MemoryRouter) and asserts: (1) submitting an empty form shows "enter a valid email" and does not call onSuccess; (2) typing into email/password fields actually updates their values.

More to know

3No TODO/FIXME comments exist in the live (non-legacy) TypeScript source — open work is tracked via PlaceholderPage stubs and the CHANGELOG's "Unreleased" section instead.
4Theme persistence has two layers that must stay consistent: the localStorage key "autonav-theme" is read both by the inline pre-hydration script in index.html and by ThemeProvider.tsx's getInitialTheme(). Rename it in one place only and you reintroduce the theme-flash bug.
5Robot selection is per-user localStorage state (key "autonav-selected-robot:<userId>") — not server-persisted. Switching browsers or clearing site data resets it to "first robot in the list."
6Auth state is deliberately not a Redux slice. useAuth() reads directly from the getMe RTK Query cache. Don't add a currentUser slice "for convenience" — trigger a refetchMe() instead when you need to force the session state to update.
7baseQueryWithReauth retries a request exactly once after a single shared /auth/refresh call. If the refresh itself fails, the original 401 is returned as-is — there's no explicit "force logout" side effect; it relies on the next getMe read reporting "unauthenticated" and the guards reacting.
8Form validation schemas are hand-mirrored from the backend, not shared via a common package. auth.schemas.ts and admin.schemas.ts both carry comments noting they'll drift if one side changes without the other — a shared packages/shared-types workspace is the flagged future upgrade.
9AddRobotForm no longer shows a generated secret. An earlier design apparently revealed a robotSecret once after creation; the current component's success state explicitly says "No secret to copy" — the robot identifies itself by its own robotId device id. Verify against the current code if you see references elsewhere to a one-time secret.
12Role/self-action safeguards exist only in the UI. UsersTable.tsx disables promote/demote/delete for the admin's own row (isSelf) to prevent accidental self-lockout — but this is a client-side convenience; real enforcement would need confirming server-side in PlatformServer.
