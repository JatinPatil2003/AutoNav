01

Purpose & Role in the System

PlatformServer is the cloud/VPN-hosted backend of AutoNav. It runs on a server that is not the robot itself (an AWS EC2 instance, reachable at platform-server.autonav.in behind nginx — see the comments in src/app.ts referencing AWS/nginx/platform-server.autonav.in.conf). Think of it as the "brain" that knows about accounts, robots, and who is allowed to drive which robot — it never talks to ROS2 or motors directly; that is RobotServer's job.

Three different kinds of things connect to it:

  1. End-user browsers — the PlatformApp React dashboard, which calls PlatformServer's REST API (/api/...) and opens a WebSocket (a persistent, two-way socket connection, as opposed to one-off HTTP requests) to /ws/control for remote-control sessions.
  2. The Android app (AndroidApp) — a Capacitor-wrapped (a native Android shell around a web app) mobile client, same REST/WebSocket surface, but using Bearer tokens instead of cookies and native Google Sign-In.
  3. Robots themselves — each physical robot runs RobotServer, which (a) dials out and holds open a persistent WebSocket to /ws/robot-link so PlatformServer can push teleop commands and run health checks, and (b) makes outbound REST calls to /api/robot-auth/* for its own kiosk login needs (checking if a user exists, fetching the roster of users allowed to log into its touchscreen, PIN setup).

PlatformServer is the central authority for three things:

  • Identity: who has an account, how they log in (password, Google), and whether they're an admin.
  • Fleet management: which robots exist, their provisioning secrets, and which users are assigned to which robots (and with what access level).
  • Remote-control session brokering: when a user wants to drive a robot from the dashboard/app, PlatformServer is the relay in the middle — it never runs the robot's control loop itself, it forwards validated commands over the already-open robot-link socket and relays the robot's health back.

04

Architecture Layers & Patterns

The layering

Why the interface sits between service and the concrete repository: a service class's constructor takes the interface type (e.g. constructor(private readonly userRepository: IUserRepository) in user.service.ts), never the concrete MongooseUserRepository class. This is "dependency inversion" — the service doesn't know or care how data is stored, only what operations are available. In production (src/app.ts), the real MongooseUserRepository is passed in. In unit tests, a hand-written in-memory class implementing the same interface (tests/unit/fakes/FakeUserRepository.ts) is passed in instead — no real MongoDB, no network, tests run in milliseconds. The fakes even replicate Mongoose-specific quirks the services depend on, e.g. FakeRobotAssignmentRepository's populateRobot/populateUser helpers mimic .populate() so a service's "is this field populated or still just an ObjectId?" check behaves identically in tests and production.

src/app.ts is the composition root: the one place in the whole codebase where concrete classes are new'd up and wired together. Everywhere else only sees interfaces/abstract types.

End-to-end trace: "robot access request" feature

From a user clicking "Request Access" in PlatformApp through admin approval to the user actually getting access.

The DTO pattern (*.dto.ts files)

A DTO ("Data Transfer Object") is a plain function/interface that converts an internal Mongoose document into exactly the JSON shape that should cross the wire — and nothing more. This exists for two reasons visible throughout this codebase:

  • Hiding sensitive/internal fields: UserModel has passwordHash (select: false in the schema already, but the DTO is the second line of defense) — toPublicUserDto never includes it. RobotAssignmentDto exposes a derived pinSet: boolean instead of the raw pinHash.
  • Decoupling the wire contract from the storage schema: RobotDto (admin, includes vpnHostname/status/lastSeenAt) vs. RobotSummaryDto (non-admin, just id/robotId/name/displayName) are two different views over the same IRobotDocument — robot.dto.ts has toRobotDto and toRobotSummaryDto side by side. Changing the Mongoose schema doesn't automatically change what's sent to clients; you only change the DTO function if you want that.
  • Several DTO files (robotAccessRequest.dto.ts, robotAssignment.dto.ts) also handle a Mongoose-specific wrinkle: a ref'd field (like request.user) might be just an ObjectId or a fully populated document depending on whether .populate() was called upstream — the DTO function runtime-checks which case it got (isUserPopulated) rather than assuming.
05

Key Flows

Eight flows, each traced step-by-step against the real files and method names.

(a) Signup / login with email + password

Trigger: user submits the signup or login form · Browser/App → auth.routes.ts → AuthController → AuthService → IUserRepository → MongoDB
  • Login: AuthService.login calls findByEmailWithPassword (the only query that .select("+passwordHash")s the normally-hidden hash) and comparePassword; 401 UnauthorizedError on any mismatch — same generic message for "no such user" and "wrong password" so it doesn't leak which one.
  • Refresh: POST /api/auth/refresh reads the refresh cookie/body, verifyRefreshToken, then compares its tokenVersion against the user's current refreshTokenVersion in the DB — logout or a password reset increments that counter, instantly invalidating every refresh token issued before that point without needing a token blocklist.

(b) Email OTP verification flow (password reset)

Trigger: user clicks "Forgot password" · Browser/App → auth.routes.ts → AuthController → AuthService → IEmailOtpRepository + IEmailOtpSender (Nodemailer/Gmail) → MongoDB

(c) Google OAuth login flow (browser + native)

Trigger: "Sign in with Google" · Browser → GET /api/auth/google → Google's consent page → GET /api/auth/google/callback → AuthController → AuthService → MongoDB

If a local-password account already exists with the same email, it gets the Google identity linked via linkGoogleAccount, which $addToSets "google" into authProviders without touching the password.

(d) Robot registration / onboarding by admin

Trigger: admin runs npm run seed:robot (first robot) or calls the admin API · Admin → robot.routes.ts/seedRobot.ts → RobotService → IRobotRepository → MongoDB. No robot participates yet — this is purely a database record.

(e) Robot access request + admin approval → robot assignment

Full trace already drawn in §04's end-to-end diagram (steps 1–11 above). Summarized here as a flow.

(f) Robot connecting to PlatformServer (robot-link: registration, persistent WS, auth)

Trigger: RobotServer boots or reconnects · RobotServer → /ws/robot-link upgrade → WsRouter → RobotLinkGateway.authenticate → IRobotRepository → RobotConnectionRegistry

robot-link vs. robot-auth — not the same thing

robot-link is the always-open, bidirectional, PlatformServer-initiated-protocol connection for teleop/health. robot-auth (flow h) is one-off outbound REST calls from RobotServer, used only for the kiosk's own human-login needs. See the dedicated diagram in flow (h) below.

(g) Remote control session flow (control module)

Trigger: a user opens the teleop screen for a robot they have access to · Browser/App → /ws/control upgrade → ControlSessionGateway → ControlSessionService → RobotConnectionRegistry → the robot's live /ws/robot-link socket → RobotServer

Termination paths — all funneled through one terminateSession

(h) robot-auth module purpose — vs. robot-link

robot-link and robot-auth solve two unrelated problems and must not be confused. This is the subtlest piece of the architecture — worth its own close diagram.

PIN-setup steps (new user logging into a robot's touchscreen for the first time)

  1. RobotApp → RobotServer → POST /api/robot-auth/check-user {email} → {exists: boolean} — not anti-enumeration: a robot is already a trusted caller, and the UX genuinely needs to distinguish "sign up first" from "ask your admin".
  2. POST /api/robot-auth/pin-setup/request-otp {email} (rate-limited by robotOtpRateLimiter, keyed by robotId:email) — is anti-enumeration (always 200): silently no-ops unless the email belongs to a user with an active assignment to this exact calling robot, reusing the OTP machinery with purpose: "robot-pin-setup".
  3. POST /api/robot-auth/pin-setup/verify-otp {email, otp} → {pinSetupToken}, a JWT binding {sub: userId, robotId: callerRobotId, purpose: "robot-pin-setup"} — the robotId is baked in at verify time, from the robot that called verify, not confirm.
  4. POST /api/robot-auth/pin-setup/confirm {pinSetupToken, pin}: checks payload.robotId !== callerRobotId and 401s if they differ — a token minted for robot A can never be used to set a PIN on robot B, even by a legitimate different robot. PIN is bcrypt-hashed and stored on the assignment.
  5. GET /api/robot-auth/roster — called by RobotServer on boot/periodic resync — returns every active, hmiAccess-enabled assignment for the calling robot including the bcrypt pinHash, so RobotServer can validate kiosk PIN logins completely offline.

Cross-Component Interaction

How RobotServer connects in

  • Identity: a robot's identity is its robotId (a device slug, e.g. autonav-01), established once at provisioning time (RobotService.createRobot / scripts/seedRobot.ts) and resolved on RobotServer's own side via its ESP32 bridge / DEV_DEVICE_ID_OVERRIDE.
  • Secret: a single shared secret (ROBOT_LINK_SECRET, 32 random bytes, sha256-hashed at rest as Robot.linkSecretHash) authenticates the robot for both /ws/robot-link (checked once, at WS handshake) and every /api/robot-auth/* call (checked per-request).
  • Persistent connection: exactly one /ws/robot-link WebSocket per robot. Heartbeats: a server-side ping every 10 seconds; force-closed after 2 consecutive missed pongs (~20–30s to detect a dead link). A reconnecting robot always wins over its own previous connection (old one closed with code 4409).

Public reachability, not VPN-gated

Per comments throughout the code (app.ts, resolveRobot.middleware.ts, robotAuth.routes.ts), both /ws/robot-link and /api/robot-auth/* are now reachable from the public internet (via nginx), not gated by a VPN boundary — the shared secret + timing-safe comparison is the entire trust boundary for robot-originated traffic. HttpRobotNotifier (PlatformServer→robot) is the one piece that still relies on the VPN, since it has no auth of its own.

How PlatformApp and AndroidApp call in

  • REST base paths: /api/auth, /api/users, /api/robots (public summaries + health), /api/robot-access-requests, /api/admin/* (admin-only), all mounted in src/app.ts.
  • Auth scheme: web clients rely on httpOnly cookies set by setAuthCookies; native/mobile clients send Authorization: Bearer <accessToken> and additionally pass X-Client: mobile so AuthController also returns the raw token pair in response bodies.
  • CORS: explicitly allow-lists config.frontendUrl plus three fixed Capacitor WebView origins and one local dev port (5190) — never a wildcard, since credentials: true is required.
  • WebSocket endpoint: /ws/control?robotId=<mongo id>, auth via cookie (web, reparsed manually) or Sec-WebSocket-Protocol: bearer, <token> — the only JS-settable way to carry a bearer token on a WS handshake without leaking it into logs via the URL.

HttpRobotNotifier — PlatformServer pushing data out to a specific robot

src/modules/robot-assignments/HttpRobotNotifier.ts implements IRobotNotifier. It is the only place PlatformServer calls out to a robot's own RobotServer unprompted (as opposed to relaying over the already-open robot-link socket). It fires after an admin revokes an assignment, or flips hmiAccess to false, calling POST https://<robot.vpnHostname>/api/platform-auth/roster/invalidate directly — no authentication of its own (the VPN/network path to vpnHostname is the trust boundary), on a short timeout (ROBOT_CALL_TIMEOUT_MS, default 5s), and is explicitly best-effort: failures are logged and swallowed (.catch(() => undefined)) because RobotServer self-corrects via its own periodic roster resync regardless.

Gotchas & Things a New Developer Must Know

Two completely separate "caller" identities, never to be confused

req.user (a human, set by requireAuth, JWT-based) vs. req.robot (a robot, set by resolveRobot, shared-secret-based) — enforced at the type level in src/common/types/express.d.ts as two distinct optional fields on Express.Request, specifically so a handler can't accidentally treat one as the other.

Refresh-token revocation is a counter, not a blocklist

User.refreshTokenVersion is compared against the tokenVersion baked into each refresh JWT at the time it was issued. Logout and password-reset both just $inc this counter — every refresh token issued before that moment instantly fails on its next use. There is no token-blocklist table to maintain, but it also means you cannot revoke one specific device's session without logging out every device.

Rate limiting is stacked, and robot-facing limiters key differently

authRateLimiter (20/15min, IP-keyed) wraps the whole /api/auth router; otpRateLimiter (5/hour, IP-keyed) additionally wraps just the OTP-adjacent endpoints. On the robot side, robotAuthRateLimiter/robotOtpRateLimiter key by x-robot-id (or robotId:email) instead of IP — because many physical robots can share one VPN egress IP, IP-keying there would let one noisy robot starve every other robot's budget.

Error → HTTP status mapping is centralized — never set res.status() yourself

errorHandler.middleware.ts (the last middleware registered in app.ts): a thrown ZodError → 400 with a details array; any AppError subclass → its own statusCode (UnauthorizedError=401, ForbiddenError=403, NotFoundError=404, ConflictError=409); anything else → 500, logged via logger.error. Always throw — and asyncHandler is what actually gets a thrown/rejected async error to that handler at all (a raw async Express handler that throws does not automatically reach errorHandler without it).

Timing-safe secret comparison appears twice, deliberately duplicated

Both robotLink.gateway.ts and resolveRobot.middleware.ts independently sha256-hash the presented secret and compare with crypto.timingSafeEqual rather than ===, specifically to prevent a timing side-channel attack (measuring response-time differences to guess the secret byte-by-byte). If you ever add a third robot-secret-checking code path, copy this pattern, not a plain string comparison.

The CHANGELOG.md is stale relative to the code

It documents auth, robot-access-requests, and early admin features in detail but has no entries for the control, robot-link, or robot-auth modules, nor for the hmiAccess/platformAccess split or the two migration scripts — all of which clearly exist and are wired into app.ts. Don't trust the changelog as a complete feature inventory; read the modules directly.

Data-model evolution is visible in scripts/

migrateRobotAssignments.ts reveals that the system originally had a one-to-one User.robot/Robot.assignedTo relationship, later migrated to the current many-to-many RobotAssignment junction collection. backfillAssignmentAccessFlags.ts similarly reveals that hmiAccess/platformAccess were originally a single implicit "has access" concept, later split into two independently-toggleable flags (kiosk login vs. dashboard/remote-control access). Both scripts are safe to re-run (upsert / only-touch-missing-fields) if you're ever unsure whether they already ran against a given database.

The control-session relay is intentionally fragile in one specific, documented way

If the robot's /ws/robot-link connection drops mid-session, ControlSessionService.handleRobotDisconnect terminates every session on that robot with state: "robot_offline" — but unlike every other termination reason, it does not attempt to send teleop.release first (there is, by definition, no link left to send it over). This is correct — you can't message a socket that just closed — but a new developer reading only the client-facing contract might wonder why that one SessionState skips the release message. It's deliberate, not a bug.

Velocity commands are coalesced, but e-stop never is

Joystick frames arriving faster than 30/s are silently collapsed to "latest value wins" before forwarding (COALESCE_INTERVAL_MS). If you add a new safety-critical frame type to controlSession.protocol.ts, follow the e-stop pattern (forwardClientFrame's early, immediate, un-coalesced send) — never the joystick pattern.

A revoked/expired assignment doesn't kill a live control session instantly

ASSIGNMENT_REVALIDATE_INTERVAL_MS is 30 seconds, and the revalidation check fails open on a transient DB error (.catch(() => true), with a comment explicitly justifying this as "don't kick a live session over a blip"). So there's up to a ~30-second window between an admin revoking access and an in-progress teleop session actually being cut off.

listAllSummaries/findSummaryByRobotId are deliberately "safe for any authenticated user"

Not just admins — they exist specifically so the request-access picker UI can show robot names without ever leaking vpnHostname or status to a non-admin. If you add a new field to RobotModel, default to not adding it to RobotSummaryDto/toRobotSummaryDto unless it's genuinely meant to be public to every logged-in user.

No TODO/FIXME comments anywhere in src/ or scripts/

The inline comments that do exist are unusually thorough design-rationale notes (e.g. why CORS is needed even "same-origin" in prod, why Sec-WebSocket-Protocol carries the bearer token, why robotAuth.checkUserExists breaks the anti-enumeration pattern on purpose) and are worth reading in place rather than skimming past — several of them explain why a line of code looks the way it does in a way this doc only summarizes.
